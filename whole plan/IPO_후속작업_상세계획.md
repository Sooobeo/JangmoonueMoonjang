## 1. 이 프로젝트에서 하려는 일

우리는 기업이 공개한 IPO, 즉 기업공개 자료를 AI에게 검토시키려 한다. IPO 자료에는 회사가 주식을 얼마에 팔지 검토하면서 어떤 이익, 비교기업, 주식수와 산식을 사용했는지가 담겨 있다. AI는 그 숫자를 다시 계산하고, 그 숫자를 비교에 쓰는 이유와 한계를 설명하고, 자료가 부족하면 무엇을 더 확인해야 하는지 적는다.

핵심 범위는 국내 비금융 기업의 IPO 중 **이미 발생한 이익으로 PER 평가를 한 사례**다. PER은 주식의 시장가치가 이익의 몇 배인지를 나타낸다. 여기서 '몇 배'라는 값을 배수라고 부른다. 비교기업의 PER을 발행사의 적용 순이익에 곱하면 주식 전체의 평가액을 얻고, 이를 적용 주식수로 나누면 주당 평가가액을 얻는다. 실제 기업에서는 이익의 기간과 범위, 비교기업의 사업 차이, 주식수의 구성이 중요하므로 계산과 판단을 함께 살핀다.

한 건을 잘 처리했다는 것은 공시의 숫자와 같은 답을 한 번 적었다는 뜻만으로 정할 수 없다. 올바른 숫자를 골랐는지, 계산이 맞는지, 공시에 있는 사실이 보고서의 판단을 뒷받침하는지, 중요한 미확인 사항을 지나치지 않았는지를 따로 확인한다. 이 확인 순서와 채점 기준을 실제 사례에 적용해 보는 것이 첫 실행의 목적이다.

결과는 **선정한 공개 IPO 자료와 평가 기준, Terra 모델과 실행 설정 아래에서 관찰한 성능**으로 설명한다. 사용자와의 대화에서 이 정도의 해석 범위면 충분하다고 정리했다. 공시가 공개된 이후의 산정 근거를 재검토하는 연구이며, 상장 이후 주가나 발표 전 공모가격 예측을 핵심 성과로 삼지 않는다.

## 3. 모델, 예산과 비교 조건

### 3.1 Terra에 어떻게 일을 맡기는가

작업 기준 모델은 **GPT-6.1 Terra**다. Python 프로그램에서 OpenAI의 Responses API를 호출한다. API는 프로그램이 모델에 요청을 보내고 답을 받는 연결 방식이다. API 키는 계정으로 그 요청을 보낼 때 필요한 비밀 인증값이다.

먼저 사용할 계정이 모델에 접근할 수 있는지, 어떤 모델 이름과 버전을 기록할 수 있는지, 실제 응답과 사용량이 어떻게 돌아오는지 확인한다. 처음 등록한 키는 인증이 거부됐지만, 사용자가 키를 교체한 뒤 인증과 실제 Terra 응답을 확인했다. 인증 실패와 개발 중 제출 실패도 원래 실행 번호에 그대로 보존했다. 최종 유효 제출은 새로운 실행 번호로 저장했으며, 상세 이력은 작업기록에 있다.

모델의 추론 설정은 답을 만들 때 문제를 얼마나 깊게 검토하도록 할지 정하는 값이다. 첫 B 파일럿은 `medium`으로 실행했다. 파일럿은 본 실험 전에 실제 사례로 절차를 시험해 보는 단계이며, 최종 비교를 시작하기 전에는 세 조건에 적용할 공통 추론 설정을 확정하고 기록한다.

### 3.2 같은 모델에 세 가지 진행 방식을 적용한다

| 이름 | 일을 진행하는 방식 | 확인하려는 점 |
|---|---|---|
| B | 프로그램이 정해 둔 조회·추출·계산·검토 순서를 따른다. | 정해진 업무 순서만으로 어느 정도 검토할 수 있는가 |
| A0 | Terra가 중간 결과를 보고 다음 검색·열람·계산을 고른다. | 다음 행동을 고르는 자유가 도움이 되는가 |
| A1 | A0가 개발 사례에서 실제로 보인 실패에 대응하는 확인·재검토 절차를 붙인다. | 추가한 절차가 새로운 기업에서도 도움이 되는가 |

세 방식은 같은 모델 버전, 자료, 공통 방법서, 기본 도구, 최종 답변 형식과 자원 상한을 사용한다. B와 A0도 자료 부족을 표시하고 추가 자료나 사람 검토를 요청할 수 있다.

공통 계산기와 공통 제출 형식 검사는 세 방식에 모두 제공한다. A1의 추가 부분은 실제 개발 실패에 대응해 붙인 확인 신호와 재검토 순서다. A1의 추가 호출과 수정 비용도 같은 실행의 총사용량에 넣는다.

### 3.3 전체 규모와 비용 목표

기본 목표는 개발 10기업과 최종 평가 20기업이다. 먼저 시험할 HDMS·멜콘·디티에스 3기업은 개발 10기업에 포함한다. 최종 평가는 20기업에 B·A0·A1을 각각 두 번 실행하므로 120회다. 기업은 20곳이고, 120은 실행 횟수다.

자료 확보나 규리의 실제 작업시간 때문에 기본안이 어렵다면 개발 6기업·평가 12기업·최종 72회의 축소안을 사용할 수 있다. 세 방식을 유지하는 안을 우선한다. 두 방식만 가능하면 A0와 A1을 남기고, 그때에는 B와의 차이를 주장하지 않는다. 규모와 변경 이유는 최종 평가 결과를 보기 전에 정한다.

사용자의 비용 목표는 **전체 실험비 약 10만원**이다. 최종 120회와 개발·연결 점검을 합쳐 약 250회 상당으로 잡은 초기 견적은 일반 입력 단가 기준 토큰 비용 7만원과 예비비 3만원이었다. 실제 응답에 캐시 쓰기 사용량이 기록되어, 같은 토큰·실행 가정에서 이를 반영한 보수적 참고 견적도 9절에 나누어 적었다. 이 참고 계산 때문에 연구의 기업 수나 실행·시간·토큰 제한을 새로 바꾸지는 않았다.

## 4. 한 건의 검토가 실제로 진행되는 모습

Terra에게 주는 것은 허용된 공시, 공통 검토방법서, 해야 할 업무, 사용할 수 있는 프로그램 기능의 목록이다. 평가자용 정답과 채점 예시는 숨긴다.

```text
사례에 사용할 공시 버전과 날짜를 정한다.
    ↓
원문과 공통 방법서를 읽을 수 있게 준비한다.
    ↓
B 프로그램이 정해진 자료를 검색하고 필요한 표·주석을 연다.
    ↓
Terra가 공시의 숫자와 출처를 정해진 칸에 적는다.
    ↓
프로그램이 그 입력으로 계산하고 결과를 돌려준다.
    ↓
Terra가 적용 이익·비교기업·대안 계산·남은 확인사항을 검토한다.
    ↓
최종 답변과 실제 자료 조회·계산·사용량 기록을 저장한다.
    ↓
이번 요청의 범위는 여기까지다. 이후 규리가 답변을 채점한다.
```

이번에 먼저 만들 B에서는 프로그램이 순서를 정한다. 나중에 만드는 A0에서는 Terra가 “이 표를 더 읽겠다”, “이 값을 다시 계산하겠다” 같은 다음 행동을 선택하게 된다. 이 차이를 비교하려면 원문 접근 기능, 계산 기능과 기록 방식은 처음부터 공통으로 쓸 수 있어야 한다.

### 4.1 ‘도구 사용을 확인한다’는 말의 뜻

여기서 도구는 모델에 붙이는 프로그램 기능이다. 예를 들어 `search_corpus`는 허용 문서 안에서 검색하는 기능이고, `read_source`는 찾은 페이지의 본문과 표를 여는 기능이며, `calculate`는 전달받은 숫자로 계산하는 기능이다.

A0를 예로 들면 Terra가 주식수 산정표를 찾으려고 검색 요청을 보낸다. Python 프로그램이 그 요청을 실행하고 관련 위치를 돌려준다. Terra는 그 표와 주석을 열고 숫자를 읽은 뒤 계산을 요청한다. B는 이 순서를 프로그램이 미리 정해 실행한다.

| 관찰한 상황 | 무엇을 확인하는가 | 어떻게 기록하는가 |
|---|---|---|
| 자료 검색 요청이 들어왔다. | 프로그램이 실제로 요청을 실행했는가 | 요청 내용, 실행 결과, 오류를 남긴다. |
| 검색 결과가 돌아왔다. | 그 사례에 허용된 문서의 위치인가 | 문서·페이지·문서 조각 번호를 남긴다. |
| 표를 열었다. | 단위·열 제목·주석·정정 전후 구분을 읽을 수 있는가 | 반환한 범위와 잘린 부분을 남긴다. |
| 정상 원문을 받았지만 모델이 다르게 읽었다. | 어떤 기간·회사·항목을 혼동했는가 | 모델의 검토 실패로 남긴다. |
| 답변에 “계산했다”고 적혀 있다. | 실제 계산 기능을 실행했는가 | 답변의 주장과 실제 실행 기록을 대조한다. |

처음에는 프로그램의 연결이 작동하는지 확인한다. 연결 문제가 있으면 수정하고 이력을 남긴다. 정상적인 자료를 받은 모델이 잘못 읽거나 다음 행동을 잘못 고른 경우는 실험에서 관찰할 실패다.

### 4.2 ‘계산을 확인한다’는 말의 뜻

HDMS 기준표에 있는 예를 보자. 적용 주식수는 다음과 같이 계산되어 있다.

```text
공모 전 주식수 40,000,000
+ 새로 발행하는 신주 4,450,000
+ 앞으로 추가 발행될 수 있는 희석가능 주식 420,190
= 적용 주식수 44,870,190주
```

기존 주주가 파는 구주 4,450,000주는 이미 발행된 주식이다. 소유권이 바뀌는 수량이므로 발행주식수의 증가분에 다시 더하지 않는다.

이 주식수와 공시의 평가시가총액을 사용하면 다음 계산이 된다.

```text
평가시가총액 4,761,293백만원 × 1,000,000
÷ 적용 주식수 44,870,190주
≈ 주당 평가가액 106,113원
```

위 숫자는 이 계획을 설명하기 위한 평가자용 예시다. 프로그램이나 모델 지시문에 사례의 정답으로 넣지 않는다. 실제 실행에서는 Terra가 원문에서 숫자와 단위를 읽어 입력하도록 한다.

계산 기능은 전달받은 숫자를 계산한다. Terra가 구주까지 더한 잘못된 주식수를 입력했다면, 산술 자체가 정확해도 최종 답은 틀릴 수 있다. 그래서 결과만 저장하지 않고 **어느 표에서 읽은 어떤 숫자를, 어떤 단위와 식으로 계산했는지** 함께 남긴다.

표시된 PER 31.5배를 그대로 곱한 결과와 공시 평가가액의 차이도 살핀다. 공개 표의 숫자가 어느 자리까지 적혀 있는지, 더 세밀한 값으로 설명할 수 있는 차이인지 확인한다. 실제 반올림·절사 규칙을 확인하지 못했다면 그 한계를 적는다. 임의로 ±5% 이내면 맞다고 정하지 않는다.

### 4.3 ‘근거가 판단으로 이어지는지 확인한다’는 말의 뜻

계산을 끝낸 뒤에는 “이 비교기업의 PER을 이 발행사에 적용할 이유가 충분한가?” 같은 판단이 남는다. 같은 산업에 속한다는 설명 하나만으로는 비교의 의미와 한계를 충분히 보여 주기 어렵다.

예를 들어 HD한국조선해양과 HDMS는 조선 관련 수요를 공유한다. 동시에 새 선박을 만드는 신조선 건조 중심의 사업과 선박 인도 후 부품·정비 서비스 사업에는 차이가 있다. 모델이 실제 공시에서 이 사실을 확인했다면, 그 차이가 자산 부담이나 실적 변동에 어떤 의미를 갖고 PER 비교에 어떤 제약을 주는지 설명해야 한다.

평가할 때에는 다음 순서로 본다.

1. 답변에 적은 문서·페이지·표가 실제로 있는가?
2. 그 위치에 답변이 말한 사실이 있는가?
3. 그 사실이 배수 비교나 이익의 비교 가능성에 어떤 의미가 있는지 설명했는가?
4. 결론에 필요한 정보가 남았다면 무엇을 더 확인해야 하는지 구체적으로 적었는가?

자료를 근거로 그대로 수용하거나, 조건을 붙여 수용하거나, 제외하거나, 추가 자료를 요청하는 결론을 모두 허용할 수 있다. 규리는 결론의 방향만이 아니라 **사실에서 판단까지의 연결이 타당한지** 기준표로 본다.

프로그램은 문서 번호나 페이지의 존재를 확인할 수 있다. 실제 문장이 주장을 뒷받침하는지, 판단의 이유가 충분한지는 규리가 채점한다. 위치가 존재한다는 이유만으로 자동으로 정답 처리하지 않는다.

## 5. Codex와 규리가 나누어 할 일

| 일 | Codex가 맡는 부분 | 규리·사용자가 맡는 부분 |
|---|---|---|
| 원문 준비 | 자료를 모으고 버전·날짜·파일 확인값을 기록하며 표를 읽을 수 있게 정리한다. | 출처와 중요한 해석 문제를 확인한다. |
| 채점기준표 | 계산과 원문 위치를 대조할 자료, 항목과 판정 예시의 초안을 준비한다. | 원문을 확인해 기준표를 작성·검토·채택하고 최종 판정을 한다. |
| 프로그램 | 자료 검색·열람·계산·실행 순서·기록 기능을 만든다. | 연구에 필요한 범위를 확인한다. |
| 모델 실행 | 정해진 설정과 예산으로 실행하고 답변·실패·사용량을 보존한다. | 이용 계정과 결제 환경을 준비하고 필요한 계정 설정을 한다. |
| 채점 | 조건명을 가린 사본과 점수·사유 입력 양식을 만든다. | 실제 점수와 판정 이유를 기록한다. |
| 분석과 설명 | 점수를 집계하고 비교표, 불확실성 계산과 보고서 초안을 만든다. | 금융 판단과 결과 해석을 최종 확인한다. |

최종 채점자는 기존 계획대로 **규리 1명**이다. Codex가 문서를 고치거나 코드를 점검하는 일이 추가 독립 평가자를 둔 실험이 되는 것은 아니다. 외부 전문가나 두 번째 평가자 확보를 다음 단계로 가는 조건으로 추가하지 않는다.

계정처럼 실제로 없는 정보가 필요하면 그 항목을 구체적으로 확인한다. 인증과 무관하게 할 수 있는 문서 정리와 코드 점검은 먼저 진행한다. 비밀 키를 코드, 공개 문서나 실행 기록에 적지 않는다.

## 6. 이번에 진행하는 일: W01~W06

이 여섯 단계는 서로 연결된다. 사용할 문서와 규칙을 정해야 자료를 모을 수 있고, 자료를 읽을 수 있게 정리해야 검색과 계산 기능을 만들 수 있다. 그 기능이 작동해야 모델 호출을 연결하고 B의 실제 답변을 받을 수 있다.

### W01. 이번 작업에서 따를 기준과 준비 상태를 적는다

**앞뒤 맥락:** Phase 1의 문서는 준비되어 있지만, 새 프로그램의 설정과 실제 자료 준비 상태는 별도로 기록해야 한다. 이 기록이 있어야 나중에 답변이 어떤 자료와 규칙에서 나왔는지 알 수 있다.

**제가 하는 일**

- 기존 계획과 Phase 1 문서의 이름·버전·용도를 목록으로 정리한다.
- Terra 사용, 전체 약 10만원, 첫 실행 대상 HDMS라는 작업 기준을 적는다.
- 아직 확인하지 않은 계정 접근, 모델 버전, 추론 설정, 실제 표본 규모를 미정 항목으로 남긴다.
- 원문과 출력의 저장 위치를 정하고 예전 문서의 끊어진 링크를 확인한다.
- 비용을 어디에 적고, 언제 남은 예산을 확인할지 정한다.

**남길 결과:** 결정 기록, 모델·예산 설정 초안, 준비된 자료와 아직 필요한 항목의 목록.

**다음으로 넘어갈 기준:** 이번에 따를 규칙, 이미 있는 자료, 아직 없는 정보가 구분되어 있다. 완료를 주장하려면 그 기록 파일이 있어야 한다.

### W02. HDMS 원문과 출처·날짜 정보를 준비한다

**앞뒤 맥락:** 방법서와 채점기준표는 검토와 평가의 기준이다. Terra가 실제로 읽을 공시 파일은 따로 필요하다. 먼저 같은 버전의 원문을 확보하고, 그 파일을 확인할 수 있는 정보를 붙인다.

**제가 하는 일**

- DART 접수번호 `20240424000222`의 2024-04-24 정정 투자설명서와 보관 PDF가 어떻게 대응하는지 확인한다.
- 사례 번호 `HDMS-DEV-01`과 문서 번호 `HDMS-PROS-01`을 쓴다.
- 원본 파일을 그대로 보관하고 SHA-256을 계산한다. SHA-256은 파일 내용이 같으면 같은 값이 나오는 파일 확인값이다. 기준표의 값과 다르면 파일 차이를 조사한다.
- 문서에 적힌 날짜, 실제 공개일, 주가·환율 기준일, 연구에서 허용하는 자료의 마지막 시점을 각각 기록한다.
- HDMS의 자료 마감 `2024-04-24 23:59:59 KST`와 공개일의 정밀도 `DATE`, 즉 시각까지는 확인되지 않았다는 기록을 대조한다.
- PDF의 실제 페이지 번호와 문서에 인쇄된 페이지 번호의 대응을 적는다.
- 정정 전 `BEFORE`, 정정 후 `AFTER`, 현재 본문 `CURRENT`, 확인 못 함 `UNKNOWN`을 구분한다.
- 규리만 참고하는 독립 재무자료는 Terra에 허용할 문서 목록과 분리한다.

기본 문서 선택 규칙은 일반청약 시작 직전에 공개된 마지막 유효 투자설명서다. 같은 단계의 투자설명서가 없으면 증권신고서를 쓰고 이유를 적는다. 그 문서가 실제로 공개된 날의 종료 시점을 기본 자료 마감으로 삼는다. 문서 작성일이나 파일 이름의 날짜를 공개일로 대신 쓰지 않는다.

**남길 결과:** 원문 파일, 사례·문서 목록, 출처와 날짜, 페이지 대응, 파일 확인값.

**다음으로 넘어갈 기준:** 다른 사람이 같은 버전의 같은 표를 찾을 수 있고, Terra가 읽어도 되는 문서 범위를 특정할 수 있다.

### W03. 공시를 검색하고 표·주석을 열 수 있게 정리한다

**앞뒤 맥락:** 원문 파일을 저장한 다음에는 수백 페이지 중 필요한 부분을 찾을 수 있어야 한다. 검색 결과만 짧게 보여 주면 단위나 주석을 놓칠 수 있으므로, 원래 표까지 이어 읽는 기능을 함께 준비한다.

**제가 하는 일**

- PDF나 XML에서 본문과 표를 읽어 낸다.
- 표의 단위, 열 제목과 주석을 같은 묶음으로 보존한다.
- 각 문서 조각에 문서 번호, 페이지, 절 제목, 정정 전후 구분, 회사와 시점 정보를 붙인다.
- 일반 본문은 우선 약 800~1,200토큰 단위로 나눈다. 토큰은 모델이 글을 처리하고 요금을 셀 때 사용하는 단위이며 글자 수와 같지는 않다.
- 표가 커서 나누어야 하면 열 제목을 반복하고 원래 표의 어느 행인지 알 수 있게 한다.
- 로컬 검색, 즉 우리 컴퓨터의 준비된 문서 안에서 찾는 기능을 먼저 쓴다.
- 별도 사용료가 드는 외부 검색 서비스는 기본 구현에 포함하지 않는다.
- 내용이 길어서 일부만 반환할 때는 잘렸다는 사실과 이어 읽을 위치를 알린다.
- 깨진 표나 잘못 읽힌 글자를 고치면 원문 위치와 수정 내용을 남긴다.

**남길 결과:** 본문·표·주석을 담은 문서 조각 목록, 검색용 목록, 추출 품질 점검 기록.

**다음으로 넘어갈 기준:** 적용 이익, 비교기업 PER, 주식수와 사업 설명을 찾아 원래 표와 주석까지 열 수 있다. 정답을 설명하는 문장을 입력에 덧붙이지 않는다.

### W04. 자료를 찾고 계산하고 요청을 남기는 공통 기능을 만든다

**앞뒤 맥락:** 읽을 수 있게 정리한 자료와 계산 코드를 모델의 검토에 연결해야 한다. 이 기능은 나중에 B·A0·A1이 함께 쓰므로, 특정 사례의 정답과 독립적으로 만든다.

| 프로그램 기능 | 하는 일 | 함께 남기는 기록 |
|---|---|---|
| `search_corpus` | 해당 사례에 허용된 문서 안에서 검색한다. | 검색어, 조건, 반환한 문서·조각 번호 |
| `read_source` | 지정한 페이지·표·문단을 연다. | 위치, 반환 범위, 잘림 여부 |
| `calculate` | 소수 계산, 단위 변환, 합계, PER과 이익 기간 계산 등을 수행한다. | 입력·단위·출처·식·결과 |
| `sensitivity` | 평균 대신 중앙값을 쓰거나 비교기업을 제외하는 등 대안을 계산한다. | 기준값, 대안과 그 이유·출처, 변화량 |
| `request_information` | 부족한 자료가 무엇이며 왜 필요한지 요청으로 남긴다. | 질문, 관련 판단, 완료를 막는지 여부 |
| `escalate` | 사람이 더 확인해야 할 해석이나 근거 충돌을 남긴다. | 쟁점, 확인할 근거, 남은 판단 |
| `submit_review` | 정해진 항목을 갖춘 최종 답변을 받는다. | 제출 내용, 형식 오류, 제출 번호 |

소수 계산에서는 일반적인 컴퓨터 소수 표현 때문에 생기는 불필요한 차이를 피하도록 정확한 계산 방식을 쓴다. 모델이 준 숫자와 출처를 기록하되, 계산기가 입력의 원문 해석까지 맞다고 보증하지는 않는다.

대안 계산은 입력이나 가정을 바꾸면 결과가 얼마나 달라지는지 확인하는 작업이다. 예를 들어 비교기업 PER을 모두 더해 나눈 평균 대신, 크기순으로 놓았을 때 가운데 값인 중앙값을 쓸 수 있다. 값의 개수가 짝수면 가운데 두 값의 평균을 중앙값으로 쓴다. 어떤 값을 왜 바꿨는지와 결과의 변화를 함께 기록한다.

자료 요청과 사람 검토 요청은 **요청 기록**이다. 회사나 다른 사람에게 실제 메시지를 보내지 않는다. 답변을 지어내거나 요청을 남겼다는 이유만으로 문제가 해결됐다고 처리하지 않는다.

**남길 결과:** 공통 기능의 코드, 요청과 반환 항목 설명, 실제 모델을 부르지 않고 확인한 결과.

**다음으로 넘어갈 기준:** 허용 자료 접근, 계산, 요청 기록, 제출 형식 확인이 각각 작동한다. 평가자용 정답을 읽지 않아도 실행할 수 있다.

### W05. Terra 호출과 프로그램의 진행 순서를 연결한다

**앞뒤 맥락:** 공통 기능이 준비되면 “모델에 요청 → 필요한 프로그램 기능 실행 → 결과를 모델에 전달 → 최종 답변 저장”을 연결한다. 이 전체 진행을 맡는 부분이 실행 제어기다.

**제가 하는 일**

- Responses API의 실제 요청·응답과 기능 실행 결과를 연결한다.
- 한 기업을 한 방식으로 한 번 검토하는 단위를 실행 1회로 센다. 실행마다 `run_id`라는 고유 번호를 붙인다.
- 사례, B/A0/A1 구분, 반복 번호, 모델·지시문·자료·설정의 확인값을 기록한다.
- 시작과 끝, 모델 호출, 자료 조회, 계산, 오류와 재시도를 시간 순서로 저장한다.
- 대화 이력을 다시 보내는 입력도 누적 사용량에 포함한다.
- 모델이 내부 검토에 사용한 추론 토큰도 출력 사용량에 포함한다. 비공개 사고과정 자체를 제출하게 하지는 않는다.
- 총호출·토큰·시간 한도를 확인하고 마지막 제출을 위한 여유를 남긴다.
- 실제 입력·출력·캐시 사용량, 시간과 비용을 기록한다. 캐시는 같은 입력의 재사용에 따른 과금 항목이므로 실제 반환값을 구분해 적는다.
- 비밀 키는 환경 설정에서 읽고 코드·예시·기록에 노출하지 않는다.
- 실행마다 새 대화로 시작하고, 다른 실행의 답변과 평가자용 자료에 접근하지 못하게 한다.

현재 Codex 대화에는 HDMS 채점기준표와 정답 수치가 이미 들어 있다. **이 대화를 실험용 Terra의 대화 이력으로 전달하지 않는다.** 실제 답변은 공통 방법서와 허용 공시만 받은 별도의 새 API 대화에서 생성한다. 정답 폴더를 읽지 말라는 문장만 적는 데 그치지 않고, 검색 목록과 프로그램의 실제 읽기 범위도 제한한다.

공시 본문에 명령처럼 보이는 문장이 있어도 분석할 자료로만 취급한다. 그 문장이 프로그램의 업무 지시나 허용 자료 범위를 바꾸게 하지 않는다.

최종 답변은 JSON, 즉 정해진 항목 이름으로 내용을 나누어 저장하는 텍스트 형식으로 받는다. 사람이 읽을 보고서로도 정리할 수 있지만 원래 제출 내용은 그대로 보존한다.

| 제출 항목 | 들어갈 내용 |
|---|---|
| `scope` | 사례, 자료 마감, 사용한 문서, 확인 범위와 한계 |
| `calculations` | 숫자, 단위, 출처, 산식, 결과와 정밀도 설명 |
| `judgments` | J1~J4별 사실, 결론, 근거·반대 근거, 미확인 사항과 다음 행동 |
| `requests` | 부족한 정보에 대한 구체적 요청 |
| `escalations` | 사람이 추가로 확인할 쟁점과 남은 판단 |
| `memo` | 중요한 결론과 우선 조치, 최대 5개 |
| `model_reported_status` | 모델이 표시한 제출 상태 |

근거에는 문서·문서 조각·페이지와 어느 주장을 지지하는지 연결한 번호를 넣는다. 요청이 실제로 없으면 요청 배열이 비어 있어도 된다. 계산 입력이 없으면 `missing_reason`과 연결된 요청 번호를 적는다. 필수 내용이 모두 빈 템플릿을 제출한 경우와 필요 없는 요청을 비워 둔 경우는 구분한다.

초기 자원 예산은 다음과 같다. 첫 시험 결과로 조정할 수 있지만 최종 평가 전에는 세 방식의 공통 규칙으로 정한다.

| 항목 | 초기값 |
|---|---:|
| 한 실행의 모델 호출 | 최대 16회 |
| 프로그램 기능 호출 | 최대 40회 |
| 누적 입력 사용량 | 목표 120,000토큰 |
| 추론을 포함한 누적 출력 사용량 | 최대 16,000토큰 |
| 한 실행의 경과 시간 | 최대 600초 |
| A1의 확인 후 수정 | 최대 2회 |

입력 목표량은 실제 청구량과 차이가 날 수 있어 비용을 보장하는 절대 상한으로 표현하지 않는다. 최종 제출용 호출과 공통 형식 수정용 호출을 각각 최소 1회 남기고, 답변을 적을 출력 여유도 파일럿에서 정해 둔다.

**남길 결과:** 모델 연결 코드, 실행 제어기, 원본 요청·응답·행동 기록, 사용량 장부.

**다음으로 넘어갈 기준:** 준비된 인증으로 실제 호출을 할 수 있고, 시작부터 최종 제출 또는 실패까지 따라갈 수 있다. 모의 응답 점검과 실제 모델 실행은 파일과 상태에서 구분한다. 키가 준비되지 않았으면 실제 호출 전의 준비 상태로 남긴다.

### W06. B를 정해진 순서로 실행해 HDMS 답변 한 편을 받는다

**앞뒤 맥락:** 앞의 다섯 단계가 준비되면 첫 실제 답변을 만든다. 이번에는 다음 행동을 모델이 자유롭게 정하는 A0까지 만들지 않고, 프로그램이 순서를 정해 주는 B부터 끝까지 실행한다.

**B가 따를 순서**

1. 사례 번호, 공시 버전, 자료 마감과 읽을 수 있는 문서 목록을 확인한다.
2. 기업명과 문서 제목 같은 정보를 채운 고정 검색어로 이익·PER·주식수·사업 설명을 조회한다.
3. 찾은 표와 주석을 열어 모델이 정해진 양식에 숫자·단위·기간·출처를 적게 한다.
4. 추출한 값으로 계산 기능을 실행하고 공시의 결과와 비교한다. 가능한 대안 계산도 정해진 절차로 처리한다.
5. J1 적용 이익, J2 비교기업, J3 대안 계산의 영향, J4 남은 확인사항 순서로 모델이 검토하게 한다.
6. 같은 최종 형식으로 제출하게 하고 원본 답변, 실제 행동, 사용량과 상태를 저장한다.

B에서는 조회 순서와 검색 횟수·재검색 여부를 프로그램의 규칙으로 정한다. 모델이 중간 결과에 따라 마음대로 순서를 바꾸거나 검색을 반복하지 않는다. 자료가 없으면 근거 없이 값을 채우지 않고 부족한 이유와 요청을 남길 수 있다. 고정 검색어와 계산 코드에 HDMS 정답 숫자를 넣지 않는다.

**남길 결과:** B 설정과 코드, HDMS의 실제 Terra 답변 한 편, 자료 조회·계산 기록, 입력·출력 사용량과 비용, 실행 상태.

**이번 요청의 완료 기준:** 실제 Terra에서 돌아온 답변과 그 실행 기록이 있다. 오답이나 낮은 점수의 답변도 원래 결과로 보존한다. API 키 미등록, 준비 오류나 호출 실패 때문에 답변을 받지 못했다면 어디까지 준비했고 무엇이 남았는지 기록한다. 그 상태를 실제 답변 생성 완료로 바꾸지 않는다.

**현재 확인한 결과:** `0.1.4-pilot`의 [실제 답변 한 편](../ipo_agent_eval/runs/20261111T233807Z_B_2db53c6b/review.md)을 받았다. 모델 요청 2회, 프로그램 기능 호출 15회, 입력 93,434토큰과 추론 포함 출력 10,554토큰을 사용했고 형식수정은 없었다. READY는 유효한 형식으로 제출했고 완료를 막는 요청을 표시하지 않았다는 뜻이며, 내용이 모두 맞다고 채점한 결과는 아니다. 원본·상태·공통 규칙 확인은 [실제 실행 점검](../ipo_agent_eval/reports/review_protocol.md)에 남겼다.

### 이번 여섯 단계에서 하는 세 차례 자가점검

이번 요청에서는 각 단계의 결과를 만들고 다음 세 관점으로 다시 읽고 확인한다.

1. **내용이 맞는가:** 원문, 숫자, 코드의 실제 동작과 문서 설명이 맞는지 본다.
2. **정한 계획을 지키는가:** 정답 분리, 같은 조건, 예산·상태·실패 기록, 이번 작업 범위가 기존 규칙과 맞는지 본다.
3. **다른 사람이 이해하고 확인할 수 있는가:** 왜 이 일을 했는지, 무엇이 남았는지, 결과 파일을 어디에서 확인하는지 문맥을 이어 썼는지 본다.

각 점검에서 찾은 문제와 고친 내용, 아직 확인하지 못한 부분을 보고서로 남긴다. 이 점검은 Codex가 문서와 구현을 검토하는 작업이다. A1이 실험 중 수행할 추가 확인과 수정 횟수, 또는 규리의 답변 채점과 구분한다. 이 문서의 개정에 대한 세 차례 점검은 [문서 점검 기록](../ipo_agent_eval/reports/review_documentation.md)에 남긴다.

## 7. 첫 B 답변을 받은 뒤 이어 갈 일: W07~W14

다음 단계들은 전체 프로젝트에 필요하지만 이번 첫 답변 생성 요청에서는 이후 작업으로 남긴다. 앞 단계의 실제 결과를 보고 순서대로 이어 간다.

### W07. 규리가 HDMS 답변을 채점할 수 있게 정리하고 실제 시간을 잰다

**앞뒤 맥락:** 답변을 받았다면 이제 기준표로 평가할 수 있는지 확인한다. 실행에 성공했다는 사실과 검토 내용이 맞다는 판단을 여기서 구분한다.

제가 조건명·반복 번호·실행 순서를 가린 답변 사본과 채점 양식을 만든다. HDMS는 F1~F5의 사실, K1~K3의 계산, J1~J4의 판단을 기록한다. 답변 문장, 인용 위치, 점수와 이유를 연결하고, 기준표의 모호한 부분이나 예상하지 못한 타당한 지적은 따로 적는다.

규리는 원문과 기준표를 대조해 실제 점수와 이유를 남기고 기준표를 채택하거나 수정한다. 자료 정리, 기준표 작성, 답변 채점에 든 시간을 각각 기록한다. 이미 끝난 과거 작업의 시간을 실제로 재지 않았다면 미측정으로 남긴다.

**남길 결과와 완료 기준:** 실제 채점표, 판정 이유, 시간 기록과 보완 목록이 있다. 어떤 문장에 왜 그 점수를 주었는지 알 수 있고, 모델의 누락·오답과 기준표 자체의 판정 불가를 구분할 수 있다.

### W08. 멜콘·디티에스도 준비해 파일럿 3기업을 끝까지 시험한다

**앞뒤 맥락:** HDMS는 연간 이익을 쓰는 사례다. 이 방법을 중간실적의 연환산, 이익 조정, 정정 전후 표에도 적용해 보려면 다른 사례가 필요하다. 연환산은 반기 같은 중간 기간의 이익을 한 해 수준으로 환산하는 것이며, 최근 12개월 이익을 뜻하는 LTM과 구분한다.

두 기업에서도 대표 공시, 접수번호, 공개일과 청약 시작일을 확인한다. 자료 마감, 이익의 기간·조정, 독립 원천 확인 범위를 적고 원문과 재계산을 바탕으로 기준표 초안을 준비한다. 규리가 원문을 확인해 기준표를 채택한 다음 B의 같은 기본 절차로 실행하고 채점한다.

세 기업의 결과를 함께 보면서 자료를 찾는 방법, 표를 읽는 방식, 계산과 채점에서 무엇을 보완할지 정리한다. 문서에 오류가 반드시 있어야 하는 것은 아니다. 근거에 따른 수용, 조건부 판단이나 추가 확인 등 실제 판단 과제가 있으면 포함할 수 있다.

**남길 결과와 완료 기준:** 세 기업의 입력 자료, 기준표, 실행·채점 기록과 시간 측정이 있다. 세 기업은 개발용으로 고정하고 최종 평가용으로 돌려쓰지 않는다.

### W09. 같은 기준으로 후보를 모으고 개발용과 평가용을 나눈다

**앞뒤 맥락:** 파일럿을 통해 자료 준비와 채점에 필요한 작업량을 알게 되면 전체 규모를 정할 수 있다. 시스템을 고칠 때 본 기업과 마지막 성과를 확인할 기업을 나누어야, 익숙한 기업에만 맞춘 결과인지 살필 수 있다.

DART와 KIND를 출발점으로 후보를 모으고 포함·제외 이유를 적는다. 기존 모집 기간 제안은 2023-01-01~2026-10-26이며, 실제 사용할 기간을 최종 모집 전에 정한다. 바꾸면 이유를 남긴다.

| 살펴볼 조건 | 처리 |
|---|---|
| 국내 비금융 IPO, 이미 발생한 실적의 PER이 주된 방법 | 다른 자료 요건도 충족하면 포함 후보로 둔다. |
| 적용 이익·비교기업·배수·주식수·산정 설명을 확인할 수 있음 | 원문과 시점을 보존하고 기준표를 만들 수 있는지 확인한다. |
| 금융회사·SPAC(기업인수목적회사)·REIT(부동산투자회사) | 핵심 자료 범위에서 제외한다. |
| 미래 추정이익 PER, EV/EBITDA나 DCF가 주된 평가 | 다른 방법을 다루는 확장 범위로 남긴다. |
| 핵심 원문이나 공개 시점을 확인할 수 없음 | 제외 이유를 기록한다. |
| 철회 거래 | 같은 자료 요건을 충족하면 후보로 둔다. 철회 공시 직전 마지막 공개 산정 문서를 사용한다. |
| 아직 대표 문서 선택 단계에 이르지 않은 진행 중 거래 | 예비 목록에 남기고 처리 이유를 적는다. |

EV/EBITDA는 기업 전체의 가치를 영업실적의 한 지표와 비교하는 방법이고, DCF는 미래 현금흐름을 현재 가치로 계산하는 방법이다. PER과 산식·판단이 다르므로 이 연구의 핵심 범위에서 분리한다. 각 사례에는 연간·LTM·중간실적 연환산, 이익 조정, 해외 비교기업 포함, 코스피·코스닥 구분도 적는다.

실제 적격 사례 수와 규리의 작업시간을 보고 개발 10·평가 20 또는 축소안을 선택한다. 이미 자세히 분석한 기업은 개발용으로 고정하고 나머지를 고정된 배정 프로그램으로 나눈다. 배정에 쓰는 난수 시작값은 `20261026`이다. 이 값을 기록하면 같은 목록으로 배정을 다시 따라 할 수 있다.

이미 분석한 기업이 3개라면 기본안에서 개발 7개와 평가 20개를 추가 배정한다. 더 분석한 기업이 생기면 그 수를 갱신하고, 개발 목표보다 많아지면 분할 계획을 바꾸어 기록한다. 같은 발행기업의 정정본을 개발과 평가에 나누지 않는다. 여러 사례가 같은 비교기업 문서를 공유하는 경우도 적는다.

**남길 결과와 완료 기준:** 후보 모집대장, 포함·제외 이유, 기업별 배정 목록과 배정 코드가 있다. 상장 성공 여부나 모델 점수를 보고 유리한 사례만 남기지 않는다.

### W10. A0가 다음 행동을 선택하게 하고 실제 실패를 모은다

**앞뒤 맥락:** B의 고정된 순서와 비교하려면 모델이 다음 행동을 고르는 A0를 만들어야 한다. 여기서 관찰한 실패가 A1에 무엇을 추가할지 정하는 근거가 된다.

B와 같은 모델·자료·방법서·기본 기능·최종 형식·자원 상한을 제공한다. 그 안에서 다음 검색, 원문 열람, 계산과 제출 시점을 모델이 선택하게 한다. 사례별 정답 힌트와 A1 전용 검사 결과는 제공하지 않는다.

개발 기업에서 B와 A0를 실행하고 규리의 채점과 실제 행동 기록을 연결한다. 실패마다 단순히 “주식수가 틀렸다”고만 적지 않고, 어떤 표를 읽고 어느 구획·단위·항목을 혼동했는지 적는다.

```text
실패 번호 → 사례·실행 번호 → 원문과 실제 행동의 증거
→ 잘못된 단계 → 결론에 준 영향 → 실행 중 알아낼 수 있는 신호
→ 대응할 기능 후보 → 기대 효과 → 새로 생길 수 있는 문제
```

준비된 자료의 누락, 저장소 안에 있는데 못 찾은 검색 실패, 잘못 읽은 숫자, 산술 오류, 시점·기간 혼동, 근거 없는 판단, 불필요한 보류를 구분한다. 수집하지 않은 공개 자료와 실제로 공개되지 않은 자료도 구분한다.

**남길 결과와 완료 기준:** B/A0 개발 답변과 채점, 실패 목록, 대응 후보가 있다. A1에 추가할 각 절차가 실제 개발 실패와 연결되어 있다.

### W11. 그 실패를 줄이기 위한 A1을 만든다

**앞뒤 맥락:** A1은 A0에 막연히 더 많은 지식을 주는 방식으로 만들지 않는다. 개발 과정에서 어떤 실패가 관찰됐는지, 실행 중 어떤 신호로 알아낼 수 있는지, 그때 무엇을 다시 하게 할지 정한다.

| 실제 실패가 관찰된 경우의 예 | 추가를 검토할 절차 | 그래도 남을 수 있는 한계 |
|---|---|---|
| 정정 전 숫자를 현재값으로 사용 | 정정 구획 정보를 대조하고 원문을 다시 연다. | 구획 표시 자체가 잘못되었을 수 있다. |
| 단위나 산식이 맞지 않음 | 다시 계산하고 입력 단위를 확인하게 한다. | 원문에서 잘못 읽은 입력은 따로 확인해야 한다. |
| 반올림 차이를 공시 오류로 단정 | 표시 정밀도와 공개 원시값을 확인하게 한다. | 실제 계산 규칙을 확보하지 못할 수 있다. |
| 중요한 주장에 출처가 없음 | 원문 위치를 보강하거나 주장을 다시 검토하게 한다. | 위치가 있어도 주장을 지지하지 않을 수 있다. |
| 중요한 자료 부족을 지나침 | 없는 자료와 그 때문에 막힌 판단을 구체화하게 한다. | 요청 자체가 불필요할 수도 있다. |

이 표는 가능한 대응을 설명하는 예다. 실제 채택 여부는 개발 실패를 보고 정한다. 기업의 정답 숫자나 특정 결론을 프로그램에 넣지 않는다.

수정 전 초안, 검사 신호, 다시 읽거나 계산한 내용, 수정 후 답변을 함께 저장한다. 추가 모델 호출도 같은 전체 예산에 넣는다. 검사기가 찾아낸 오류, 놓친 오류, 정상 답변을 잘못 막은 경우와 수정 때문에 생긴 새 오류도 볼 수 있게 한다. 모델이 말한 자신감 숫자만으로 사람 검토를 요청하게 하지 않는다.

검사기가 얼마나 잘 찾았는지 셀 때는 그 검사기가 원래 대상으로 삼은 오류를 기준으로 한다. 숫자 단위 검사기에 사업 비교의 논리까지 찾아내도록 요구한 것처럼 분모를 넓히지 않는다.

공통 계산기와 공통 제출 형식 검사는 B/A0에도 있다. A1만의 변화는 실제 개발 실패에 대응해 더한 확인 신호와 재검토 순서다.

**남길 결과와 완료 기준:** A1 코드·설정, 실패와 추가 절차의 연결표, 개발 검증 결과가 있다. 왜 추가했는지, 비용과 새 문제는 무엇인지 설명할 수 있다.

### W12. 최종 평가 전에 사용할 자료와 규칙을 정해 고정한다

**앞뒤 맥락:** 개발을 마친 다음에는 새로운 기업에서 결과를 확인해야 한다. 그 결과를 본 뒤 모델 지시문이나 채점 기준을 바꾸면 비교의 의미가 달라지므로, 시작 전에 사용할 버전을 정한다.

규리가 최종 답변을 보기 전에 평가용 기준표를 작성·검토할 수 있도록 자료를 준비한다. 모델과 API 설정, 공통 방법서, 지시문, 프로그램 기능, A1 검사기, 예산, 표본 규모와 분석 규칙을 정한다. 고정 가능한 모델 버전, 반환된 모델 정보와 실행 날짜를 기록하고 고정할 수 없는 부분은 한계로 남긴다.

기업 배정과 실행 순서를 섞는 난수 시작값을 정하는 것과 모델이 같은 답을 다시 내는 것은 별개다. 제공자가 답변 생성의 난수 고정을 지원하지 않으면 같은 설정에서도 같은 답이 보장된다고 쓰지 않는다.

사례 목록, 문서, 기준표와 지시문의 SHA-256, 코드 변경 버전 번호인 커밋 등 버전을 추적할 값을 남긴다. 정답과 다른 실행 결과를 실제로 읽을 수 없는지 확인한다. 실패·재시도·형식 수정·자료 오류 처리도 미리 정한다.

**남길 결과와 완료 기준:** 실행 전에 정한 규칙을 적은 사전등록 파일, 버전·확인값 목록, 최종 실행 목록이 있다. 필수 미정 항목이나 평가용 기준표가 부족하면 실행 시점을 조정하거나 미리 정한 축소안을 적용한다.

### W13. 새로운 기업에서 최종 비교를 실행하고 채점 사본을 만든다

**앞뒤 맥락:** 고정한 규칙으로 개발에 쓰지 않은 기업을 검토한다. 같은 기업에서도 답이 달라질 수 있으므로 각 방식을 두 번 실행하고, 다른 실행의 답은 다음 실행에 전달하지 않는다.

기본안은 120회, 축소안은 72회의 실행 목록을 먼저 만든다. 기업별 B/A0/A1과 반복 순서는 정한 난수 시작값으로 섞어 특정 방식에 장애나 시간대 영향이 몰리지 않게 한다. 각 실행은 새 대화로 시작한다.

예정한 실행마다 답변 또는 실패 사유와 비용을 보존한다. 모델의 답이 나쁘다는 이유로 힌트를 주고 다시 실행해 교체하지 않는다. 채점용 사본에서는 조건명·반복·순서를 가리고, 원래 실행과 연결하는 표는 따로 둔다. 규리는 같은 기준으로 점수와 이유를 적는다. 문체로 조건을 추측할 수 있으므로 완전한 눈가림이라고 표현하지 않는다.

**남길 결과와 완료 기준:** 예정 실행 전체의 기록, 원본 답변, 조건명을 가린 채점 자료, 점수와 사유가 있다. 빠진 실행이나 중단이 있다면 목록과 이유를 그대로 보고한다.

### W14. 점수·오류·완료 범위·비용을 함께 분석해 보고서로 묶는다

**앞뒤 맥락:** 마지막에는 점수 하나만 볼 수 없다. 검토 충족률이 높아졌는지, 틀린 완료 답변이 줄었는지, 더 많이 보류하거나 더 비싸졌는지 함께 보아야 한다.

같은 기업의 두 반복을 먼저 평균한 뒤 기업별 차이를 구한다. 세 방식을 실행했다면 A0−B, A1−A0, A1−B를 비교한다. 두 방식만 실행했다면 실제로 존재하는 비교만 계산한다.

기업을 다시 뽑아 비교를 반복하는 paired bootstrap을 10,000회 수행해 차이의 95% 구간을 구한다. 쉽게 말하면, 같은 기업의 모든 방식·반복 결과를 한 묶음으로 두고 같은 기업이 여러 번 뽑힐 수 있도록 기업 묶음을 다시 선택해 차이가 얼마나 달라지는지 보는 방법이다. 분석 난수 시작값은 `20261026`을 사용한다.

비율 지표는 기업을 다시 뽑을 때마다 분자와 분모도 다시 계산한다. 분모 0인 재표집의 비중을 공개하고, 그 비중이 5%를 넘으면 해당 구간을 제시하지 않는다. 이는 미리 정한 보고 규칙이며 성능을 보장하는 문턱이 아니다.

판정 가능한 기업 수와 제외 이유, 공유 비교기업 문서, 규리 한 명의 판단, 모델이 과거 공개자료를 이미 학습했을 가능성을 함께 적는다. 검사기가 놓치거나 잘못 경고한 부분과 A1 수정 전후의 변화도 구분한다.

같은 조건의 두 반복에서 판단 상태가 달라진 비율과 점수 차이도 따로 적는다. 연환산 여부, 원천 확인 수준, 해외 비교기업 포함 여부로 나누어 보는 결과는 탐색적으로만 설명한다. 결과를 본 뒤 유리한 기업 묶음만 골라 제외하지 않는다.

**남길 결과와 완료 기준:** 기업·영역·조건별 결과표, 분석 코드, 실패와 개선의 연결표, 최종 보고서가 있다. A1이 더 좋지 않아도 결과와 가능한 이유를 그대로 설명한다.

## 8. 어떤 기준으로 답변을 평가하는가

### 8.1 연구 질문을 가설 형태로 적은 초안

기존 계획서는 연구 질문과 미리 정한 비교를 중심으로 되어 있다. 다음 문장은 이를 가설 형태로 풀어 쓴 초안이다. 최종 평가 전에는 문구와 분석 계획을 정한다.

| 가설 | 비교 | 확인할 내용 |
|---|---|---|
| H1 | A0와 B | 같은 Terra·자료·자원 상한에서 다음 행동을 모델이 선택하면 고정 절차보다 방법론적 검토 충족률이 높아진다. |
| H2 | A1과 A0 | 실제 개발 실패에 대응하는 확인·재검토를 추가하면 방법론적 검토 충족률이 높아진다. |

이 연구는 탐색적 비교다. 가설이 지지되지 않아도 유효한 결과다. 비용·완료·요청·오류를 함께 보고하며, A1을 하나의 개선 시스템으로 해석한다. 개별 검사기의 효과를 따로 주장하려면 그 검사기를 빼고 비교하는 별도 실험이 필요하다. 작은 표본에서 p값 같은 통계 검정 결과 하나만으로 실무 합격·불합격이나 배포 가능 여부를 정하지 않는다.

### 8.2 사실·계산과 판단을 따로 본다

| 영역 | 확인하는 내용 | 점수·기록 |
|---|---|---|
| C0 사실 | 숫자·단위·기간·주식수·공시 결과를 맞게 읽었는가 | 필수 사실 정확도 |
| C0 계산 | 올바른 식과 단위로 계산하고 정밀도 차이를 설명했는가 | 계산 일치율 |
| J1 | 적용 이익의 기간·범위·조정이 비교에 주는 의미를 설명했는가 | 0·1·2점 |
| J2 | 비교기업의 실제 공통점·차이를 배수 판단에 연결했는가 | 0·1·2점 |
| J3 | 출처가 있는 대안으로 다시 계산하고 변화의 방향·크기를 설명했는가 | 0·1·2점 |
| J4 | 확인한 범위와 남은 쟁점을 나누고 필요한 다음 행동을 구체화했는가 | 0·1·2점 |

2점은 사실과 근거가 맞고 판단의 이유까지 충족한 경우, 1점은 관련 내용은 맞지만 중요한 연결이 부족한 경우, 0점은 누락되었거나 중요한 사실·계산·논리가 틀린 경우다. 타당한 수용도 2점이 가능하다. 경고나 보류를 많이 적었다는 이유로 점수를 더 주지 않는다.

HDMS의 C0는 사실 5묶음 F1~F5와 계산 3항목 K1~K3이다. 모든 기업의 항목 수를 이 수로 자동 고정하지 않고 사례별 기준표에서 필요한 항목을 정한다.

주로 비교할 값인 **방법론적 검토 충족률**은 각 J 영역에서 2점 항목의 비율을 구한 뒤 네 영역을 같은 비중으로 평균한다. HDMS는 영역마다 한 항목이므로 2점을 받은 J 항목 수를 4로 나눈 값이다. 0·1·2점의 총점을 만점으로 나눈 값으로 바꾸지 않고, 1점은 부분 충족으로 따로 남긴다.

제출하지 못한 필수 항목은 채점할 수 있는 항목이라면 0점이다. 반대로 기준표 자체의 근거가 부족해서 규리가 허용 답을 정할 수 없는 경우는 `GOLD_UNRESOLVED`로 적는다. 한 J 영역이라도 유효 항목이 0이면 그 기업의 주지표는 모든 조건·반복에서 `NA`, 즉 계산할 수 없음으로 처리한다. 남은 영역만 다시 평균하지 않는다. 조건 비교에는 공통으로 유효한 기업을 쓰고, 유효 기업 수와 판정 불가 이유를 보고한다. 그 기업도 계산 가능한 오류·실패·비용 지표에서는 남긴다.

### 8.3 제출 상태와 답변이 맞는지는 따로 기록한다

프로그램은 제출 형식과 실행 당시 미해결 요청을 보고 상태를 정한다. 판단 순서는 다음과 같다.

```text
유효한 최종 제출이 없다.
    → FAILED: 유효 답변을 제출하지 못함
미해결이고 blocking=true인 사람 검토 요청이 있다.
    → HUMAN_REVIEW: 사람이 더 확인할 판단이 남음
미해결이고 blocking=true인 정보 요청이 있다.
    → PENDING_INFO: 필요한 자료가 아직 없음
그 외
    → READY: 중요한 미해결 요청을 표시하지 않고 제출함
```

`blocking`은 그 쟁점 때문에 중요한 판단의 완료가 막힌다고 모델이 표시한 값이다. 요청에는 이 값, 해결 상태 `resolution_status`, 연결된 판단 번호 `related_judgment_ids`를 적는다. 핵심 실험에서 실제 후속 응답을 주지 않으므로 요청은 원칙적으로 `OPEN`이다. 허용 문서 안에서 근거를 찾아 해소한 경우만 해결 근거와 함께 `RESOLVED`로 남긴다.

`READY`는 정답이나 안전을 승인한 상태가 아니다. 규리가 나중에 틀린 답을 발견해도 READY에서 빼지 않는다. 이 오류가 완료 초안에 남은 위험이다. 모델이 보고한 상태와 프로그램이 계산한 상태를 따로 저장하고, 요청과 blocking 표시의 적절성은 규리가 평가한다.

조건을 붙여 수용한 결론이라도 중요한 미확인 정보나 사람의 해석 확인에 의존하면 그 요청을 완료를 막는 쟁점으로 표시해야 한다. 단순히 결론 문장을 적었다는 이유로 READY로 처리하지 않는다.

### 8.4 공시를 다시 계산한 범위와 원천까지 대조한 범위를 구분한다

| 표시 | 어디까지 확인했는가 |
|---|---|
| L1 | 공시에 적힌 값으로 계산을 재현했다. |
| L2 | 발행사나 비교기업이 공개한 독립 원자료와 대조했다. |
| L3 | 독립 원천을 확보하지 못했으며 그 한계를 남겼다. |

예를 들어 HDMS 공시 안에 있는 일별 종가·상장주식수·환율로 산정표를 다시 계산할 수 있다. 거래소나 데이터 공급자의 독립 자료로 그 입력을 대조하는 일은 별도다. 규리만 본 외부 자료를 모델도 확인했다고 가정하지 않는다.

자료가 어디까지 준비되어 있는지도 별도로 적는다.

| 표시 | 의미 |
|---|---|
| `AVAILABLE_IN_CORPUS` | 현재 모델 입력에 포함된 정보 |
| `PUBLIC_OUT_OF_CORPUS` | 당시 공개됐지만 현재 입력으로 모으지 않은 정보 |
| `NOT_PUBLIC_OR_NOT_PUBLISHED` | 당시 공개되지 않았거나 비공개인 정보 |
| `UNKNOWN` | 당시 공개 여부를 확인하지 못한 정보 |

이 구분이 있어야 자료 수집 누락, 저장소 안의 검색 실패와 공개정보 자체의 한계를 섞지 않는다. 새 자료를 허용 입력에 넣으면 세 조건에 함께 제공하고 관련 기준표도 같은 기준으로 갱신한다. 최종 평가를 본 뒤 바꾼 경우는 변경 이력과 결과 영향을 남긴다.

### 8.5 주지표와 나란히 보고할 값

| 지표 | 분자 / 분모 또는 기록 방식 |
|---|---|
| 필수 사실 정확도 | 맞게 읽은 필수 사실 / 미리 정한 필수 사실 |
| 계산 일치율 | 정밀도 규칙을 충족한 계산 / 검증 가능한 필수 계산 |
| 근거 지지율 | 원문이 지지하는 핵심 주장 / 제출한 핵심 주장 |
| 부당 경고 | 근거 없거나 과장한 경고 수와 전체 경고 대비 비율 |
| READY 비율 | READY 실행 / 전체 예정 실행 |
| READY 핵심 검토 오류율 | 핵심 오류가 있는 READY 실행 / READY 실행 |
| 예정 실행당 관찰된 핵심 오류 | 핵심 오류가 관찰된 실행 / 전체 예정 실행 |
| 실패 또는 핵심 오류 비율 | FAILED이거나 관찰된 핵심 오류가 있는 실행 수(둘 다이면 한 번만 셈) / 전체 예정 실행 |
| 불필요한 사람 검토 요청 | 불필요하다고 판정한 요청 / 전체 사람 검토 요청 |
| 필요한 사람 검토 요청 누락 | 필요한데 요청하지 않은 항목 / 기준표상 요청이 필요한 항목 |
| 중요한 정보 요청 미해결률 | 중요한 정보 요청이 남은 실행 / 전체 예정 실행 |
| 실행 실패율 | FAILED 실행 / 전체 예정 실행 |
| 비용·시간 | 실제 청구 비용과 소요 시간의 평균·중앙값·범위 |

핵심 오류는 사례의 필수 결론을 바꿀 수 있고 원문·산식·명시된 기준과 충돌하는 오류다. 어떤 오류와 영향을 볼지는 사례별로 적는다. 분모가 0이면 NA로 기록하고 이유와 항목 수를 함께 보여 준다. 제출물이 없는 실패를 오류 없는 답변으로 세지 않는다.

추가 사람 검토를 요청한 답변에서도 잘못된 사실과 계산은 그대로 오류에 넣는다. 사람이 나중에 고칠 것이라고 가정해 점수를 올리지 않는다. 실제 후속 검토의 시간·수정량·해결 효과는 그 작업을 실제로 수행하고 측정했을 때만 보고한다.

## 9. 약 10만원의 실험비를 관리하는 방법

### 9.1 먼저 계산해 둔 예산

2026-11-11 공식 문서에서 확인한 Terra 표준 요금은 입력 100만 토큰당 $1, 출력 100만 토큰당 $5다. 실행 때 적용되는 요금과 과금 옵션을 다시 확인한다. 아래는 캐시 할인·캐시 쓰기·유료 호스팅 도구를 반영하지 않은 토큰 비용 계산이다.

```text
한 기업을 한 방식으로 한 번 검토할 때의 모든 호출 합계:

입력 120,000토큰 × $1 / 1,000,000 = $0.12
추론 포함 출력 16,000토큰 × $5 / 1,000,000 = $0.08

합계 = $0.20
```

모델 호출 1회가 아니라 한 검토 실행 안의 모든 호출을 합친 사용량이다. 누적 입력 12만·출력 1.6만 안에서 실행한 경우의 값이며, 사용량이나 예산을 늘리면 비용도 달라진다.

| 예산 항목 | 계산 가정 | 달러 | 예산용 원화 환산 |
|---|---|---:|---:|
| 최종 평가 | 120회 × $0.20 | $24 | 33,600원 |
| 파일럿·개발·연결 점검·오류 수정 | 130회 상당 × $0.20 | $26 | 36,400원 |
| 토큰 비용 소계 | 총 250회 상당 | $50 | 70,000원 |
| 예비비 | 세금·수수료·환율·추가 실행 | 별도 | 30,000원 |
| 전체 목표 | 예산용 환율 $1=1,400원 | — | **100,000원** |

130회는 확정 실험 횟수가 아니라 돈을 나누어 잡기 위한 가정이다. 짧은 연결 시험과 긴 검토 실행은 실제 사용량이 다르므로 금액 장부로 관리한다. 인건비, 기존 구독료, 유료 데이터와 별도 서버 비용은 포함하지 않는다. 공개자료와 로컬 자료 처리를 기본으로 한다.

### 9.2 실제 응답에서 확인한 캐시 쓰기도 예산에 반영한다

첫 실행들의 원본 사용량에는 캐시 읽기와 캐시 쓰기가 기록되어 있었다. 캐시는 같은 입력을 다시 쓰기 위해 보관하는 방식이다. 새로 보관하는 입력에는 일반 입력과 다른 쓰기 요금이 적용되므로, 위 7만원 계산을 그대로 실제 청구 예상액으로 삼지 않는다.

현재 확인한 기본 30분 캐시 쓰기 요금은 100만 토큰당 $1.25다. 같은 입력 120,000토큰을 모두 새로 보관하고 출력 16,000토큰을 쓴다고 보수적으로 계산하면 다음과 같다.

```text
입력 캐시 쓰기 120,000토큰 × $1.25 / 1,000,000 = $0.15
추론 포함 출력 16,000토큰 × $5 / 1,000,000 = $0.08

한 실행 $0.23 × 예산용 환율 1,400원 = 322원
250회 상당 80,500원 + 예비비 19,500원 = 100,000원
```

일반 입력·캐시 읽기·캐시 쓰기를 같은 토큰에 겹쳐 계산하지 않는다. 이 표는 기본 30분 쓰기 단가의 참고 견적이며, 실제로 일반 입력과 캐시 읽기가 얼마나 섞이는지, 어떤 보관시간을 쓰는지에 따라 달라진다. 기존의 250회 상당이라는 가정과 공통 한도를 유지하면서 비용 계산을 더 보수적으로 본 것이다.

저장된 응답의 사용량을 종류별로 다시 계산한 최신 근거는 [사용비용](../ipo_agent_eval/reports/사용비용.md)과 [응답별 비용 계산](../ipo_agent_eval/reports/usage_costs.json)이다. 현재 유효 제출 1건의 예상 비용은 약 237.39원이며, 사용량이 확인된 실패 요청까지 합친 금액은 약 983.27원이다. 사용량을 받지 못한 인증 오류 요청 1회는 청구액을 0원으로 확정하지 않았다. 이 금액은 세금·실제 결제환율을 포함한 청구서가 아니라 원본 사용량으로 계산한 추정이다. 원래 실행 요약의 일반 입력 가정 금액과 구분한다.

### 9.3 실제로 쓴 금액을 보면서 조정한다

1. 연결 점검, 실패, 재시도, 형식 수정, A1 추가 확인 호출까지 과금된 사용량을 모두 적는다.
2. 실행 후 실제 입력·출력·캐시와 비용을 기록하고 예상과 비교한다.
3. 첫 HDMS 답변을 받은 뒤, 파일럿 3기업을 마친 뒤 전체 비용 예상치를 다시 계산한다.
4. 최종 평가에 필요한 돈은 개발 중에도 남겨 둔다.
5. 예산이 부족할 것으로 보이면 최종 평가 전에 개발 반복 수, 자료 구성, 공통 자원 예산이나 사전 축소안을 조정한다.
6. 최종 결과가 나쁘다는 이유로 유리한 조건이나 기업만 선택해 줄이지 않는다.
7. 실행기가 남은 비용과 한도를 확인하도록 만든다. 공급자의 예산 알림이 자동으로 결제를 막아 준다고 가정하지 않는다.
8. 예산 때문에 멈추면 실제 중단 시점, 미실행 목록과 이유를 남긴다. 계획한 전체 평가를 마쳤다고 쓰지 않는다.

지금의 토큰 예산으로 Terra가 필요한 검토와 최종 제출까지 끝낼 수 있는지는 아직 측정하지 않았다. 부족하면 그 실패와 사용량을 남기고 개발 단계에서 자원 예산과 전체 규모를 함께 정한다.

## 10. 실패, 재시도와 변경을 기록하는 방법

| 상황 | 처리 |
|---|---|
| 실행 시작 전 확인된 일시적인 API 통신 장애 | 같은 요청을 최대 2회 다시 시도하고 원래 시도와 비용을 남긴다. |
| 정상 원문을 모델이 잘못 읽음 | 검토 실패로 남긴다. 운영자가 정답 힌트를 주어 결과를 교체하지 않는다. |
| 제출 형식이 틀림 | 모든 조건에 같은 구조 오류 안내로 1회 수정 기회를 주고 전체 예산에 포함한다. |
| 토큰·시간·호출 한도 도달 | 마지막 내용을 저장하고 유효 제출이 없으면 FAILED로 남긴다. |
| 원문 묶음이나 추출 데이터 자체의 오류 | 수정 내용과 버전을 남기고 모든 조건에 같은 자료를 적용한다. 원래 결과와 다시 실행한 결과를 모두 보존한다. |
| 채점기준표 오류 | 규리가 수정 이유를 남기고 모든 조건·반복에 같은 규칙을 적용한다. 원래 점수와 변경 영향을 보존한다. |
| 최종 답변을 본 뒤 모델 지시문이나 검사기를 변경 | 새 탐색 버전으로 남기고 원래 최종 평가를 교체하지 않는다. |

시스템 실행 중 장애는 기본적으로 실패에 포함한다. 명백한 외부 장애를 무효로 처리할 예외가 필요하면 최종 평가 전에 정하고, 제외 전후 결과를 함께 보여 준다.

API 키 미등록처럼 실험이 시작되기 전의 준비 부족은 시작 전 점검에서 별도로 알린다. 실제 모델 호출을 했다는 기록이나 실제 답변을 지어내지 않는다. 모의 응답은 프로그램 점검용으로만 표시한다.

## 11. 만들 파일과 어디에 쓰는지

다음은 전체 구현이 진행되면서 만들 구조다. 이번 요청은 그중 W01~W06에 필요한 부분을 먼저 만든다. 이 목록에 적혀 있다고 모든 폴더와 결과가 이미 있다는 뜻은 아니다.

역할을 설명하기 위한 구조이므로 실제 구현에서 파일 이름이나 확장자는 달라질 수 있다. 이번에 실제로 만든 파일과 실행 번호는 작업기록에서 확인한다. 이름을 바꾸더라도 모델 입력과 평가자용 자료의 접근 구분은 유지한다.

```text
ipo_agent_eval/
  README.md
  preregistration.yaml
  decisions.md
  config/
    model.yaml
    budget.yaml
    B.yaml
    A0.yaml
    A1.yaml
  data/
    public/
      case_manifest.jsonl
      documents.jsonl
      chunks.jsonl
      raw/
      index/
    private/
      gold_cases.jsonl
      adjudication_log.jsonl
      grading_id_map.jsonl
  prompts/
    common.md
  src/
    ingest/
    tools/
    runner/
    validators/
    grading/
  runs/
  grading_exports/
  analysis/
  reports/
```

| 위치·파일 | 쓰임 |
|---|---|
| `decisions.md`, `preregistration.yaml` | 선택한 규칙, 미정 항목, 최종 평가 전에 정한 조건을 적는다. |
| `config/` | 모델·예산·B/A0/A1의 실행 설정을 둔다. |
| `case_manifest.jsonl` | 기업 사례별 문서·시점·포함 여부·개발/평가 구분을 적는다. |
| `documents.jsonl`, `chunks.jsonl` | 문서 출처·날짜·페이지와 읽을 수 있는 문서 조각을 적는다. |
| `data/public/raw/` | 모델 입력에 허용할 원문 파일을 보관한다. |
| `data/public/index/` | 허용된 문서를 찾기 위한 검색용 목록을 둔다. |
| `data/private/` | 정답, 규리의 판정 기록, 익명 번호와 조건의 연결표를 둔다. |
| `prompts/` | 모델에 주는 공통 업무 지시와 형식을 둔다. |
| `src/` | 문서 정리·공통 기능·실행·검사·채점 지원 코드를 둔다. |
| `runs/` | 실제 답변, 실패, 행동과 사용량을 실행별로 보관한다. |
| `grading_exports/` | 조건명을 가린 채점 사본을 둔다. |
| `analysis/`, `reports/` | 집계·분석 결과, 점검 기록과 최종 설명을 둔다. |

`public`은 모델 입력으로 허용한 자료라는 구분이다. 인터넷에 공개하거나 외부에 게시한다는 뜻이 아니다. 파일 이름이나 폴더를 나누기만 하지 않고, 모델과 그 도구가 실제로 읽을 수 있는 범위를 제한한다. 정답, 채점 결과, 다른 실행의 답변과 자료 마감 이후의 문서는 실험 입력과 검색 목록에서 제외한다.

## 12. 진행 상태와 앞으로 남길 결과

현재는 첫 B 검토 답변 한 편을 실제로 받았고, 다음 단계의 규리 채점은 아직 하지 않았다. 아래의 완료는 HDMS 한 건의 첫 B 실행에 필요한 범위를 뜻한다. 전체 기업 자료나 A0/A1이 완성되었다는 뜻은 아니다.

전체 프로젝트가 끝날 때에는 다음 묶음을 남긴다.

| 묶음 | 들어갈 내용 |
|---|---|
| 연구 설정 | 질문과 가설, 실제 선택 규모, 모델·도구·예산, 고정·변경 기록 |
| 사례 자료 | 후보 모집·제외·배정, 문서 버전·공개 시점·파일 확인값, 원문 위치와 L1/L2/L3 |
| 평가 자료 | 공통 방법서, 사례별 기준표, 규리의 점수·이유·판정 변경 |
| 실행 기록 | 예정 실행 전체, 원본 답변과 실제 행동, 실패·재시도·상태·비용 |
| 실패와 개선 | 관찰한 실패, A1에 추가한 절차, 남은 한계와 새 문제 |
| 비교 결과 | 기업·영역·방식별 점수, 오류·완료·요청·비용과 불확실성 |
| 최종 설명 | 어떤 작업을 보조할 수 있었고 무엇을 더 확인해야 하는지, 적용 범위와 한계 |

결론은 선정한 자료와 설정에서 Terra 기반 시스템에 관찰된 결과까지 설명한다. 다른 모델이나 전체 IPO 시장에도 같은 성능이 나온다고 일반화하거나, 실제로 하지 않은 사람의 후속 검토가 문제를 해결했다고 가정하지 않는다. 과거 공개자료를 모델이 이미 학습했을 가능성도 남는다.

원래 계획의 후속 공시·전향적 관찰은 선택 확장이다. 제시된 2026-11-01~11-10 기간은 현재 이미 지났으므로, 새 관찰을 하려면 별도의 미래 시점과 자료를 미리 고정하는 계획을 세운다. 이번 핵심 작업의 완료 조건에 추가하지 않는다.

## 13. 이 계획의 근거

이 문서는 다음 자료의 연구 규칙을 실제 작업 순서로 풀어 쓴 것이다. 모델 설정, 개발 실행 횟수와 예산 배분처럼 이번에 제안한 값은 제안 또는 미정이라고 표시했다.

- [프로젝트 제안서](IPO_Proposal.html): 연구 목적과 결과를 설명할 범위.
- [프로젝트 설계서](IPO_Project_Design.html): 세 방식의 비교, 규리 한 명의 채점, 표본과 작업량.
- [실험 실행 프로토콜](IPO_Experiment_Protocol.html): 3~11절의 자료·실행·채점 규칙, 12~17절의 분석과 결과물.
- [공통 검토방법서](../phase1/IPO_PER_검토방법서.md): AI가 공시를 읽고 검토하는 방법.
- [HDMS 개발용 채점기준표 v0.3](../phase1/HDMS_DEV_01_채점기준표.md): HDMS의 수치와 판정 예시.

모델 기능과 비용은 다음 공식 자료를 참고한다. 이 계획의 요금 계산은 2026-11-11에 확인한 값을 사용하며, 실제 호출을 준비할 때 적용 요금과 계정 접근을 다시 확인한다.

- [OpenAI: GPT-6.1 Terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra): 모델 이름, Responses API의 기능 호출과 표준 입력·출력 요금.
- [OpenAI: Reasoning models](https://developers.openai.com/api/docs/guides/reasoning): 추론 토큰을 포함한 출력 과금과 출력 사용량 관리.
