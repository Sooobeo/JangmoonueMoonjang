IPO 파일럿 보완과 A0 개발 상세설계

작성: 2026년 11월 13일 · 설계 버전 1.0 · 담당 규리 / 설계·검증 지원 Codex

현재는 B 방식의 3기업 개발 파일럿과 AI 보조 채점까지 마쳤다. 이 문서는 그다음에 할 공통 계산·입력·검색 보완, 추가 사례 배정, A0 구현과 개발 비교를 구체화한다. 아래의 새 필드·파일·명령·설정은 구현할 설계이며, 구현 완료를 뜻하지 않는다.

1. 기존 문서와 이번 상세설계의 관계

문서 이미 정한 내용 이번 문서가 더 구체화하는 내용
연구 설계서 연구 범위, B·A0·A1 비교, 개발/평가 분리 현재 코드에서 바꿀 데이터 구조와 실행 경로
실험 프로토콜 공통 도구, 형식 검사, 예산, 실패 보존, 최종 분석 도구 인자, 상태 전이, 예산 예약, A0 종료 계약
후속 상세계획 W09~W14의 일과 완료 기준 파일럿 후 공통 보완부터 W10까지의 구현 순서와 인수조건
최신 할 일·파일럿 종합 기록 3기업 결과와 발견한 문제 각 문제를 어떤 변경과 검증으로 닫을지

기존 후속계획의 앞부분 상태는 11월 12일 HDMS 한 건 당시다. 현재 상태는 최신 할 일과 3기업 종합 기록을 따른다. 연구 전체의 목적·평가 규칙은 위 설계서와 프로토콜을 유지하고, 이번 문서는 다음 개발 단계의 구현 세부를 보충한다.

2. 전체 프로젝트 안의 위치와 이번 작업의 끝

국내 비금융 IPO 중 과거 실적 PER 공시를 같은 모델·공개자료·방법서·도구·출력 형식·자원 상한으로 검토한다. 프로그램이 순서를 고르는 B, 모델이 다음 행동을 고르는 A0, 관찰된 A0 실패에 맞춰 확인·재검토를 추가한 A1을 비교한다. 사실·계산, 근거와 판단, 완료/보류, 비용과 시간을 함께 평가한다.

연구 질문·방법·기준 설계
  → B 구현과 3기업 파일럿 [여기까지 완료: AI 보조 채점]
  → 공통 계산·입력·검색 보완 [지금 시작할 일]
  → W09: 사례 확대와 개발/평가 배정
  → W10: 새 공통 버전의 B/A0 개발 비교와 실패 수집 [이번 설계의 끝]
  → W11: 실패에 연결된 A1
  → W12: 최종 자료·설정·채점·분석 동결
  → W13: 보지 않은 기업에서 반복 실행·채점
  → W14: 기업별 비교·비용·한계와 최종 보고

이번 단계의 완료는 공통 보완을 쓴 B와 A0가 개발 사례에서 실제로 실행되고, 항목별 채점·행동·비용·실패가 연결되어 A1 설계로 넘길 수 있는 상태다. 새 평가 기업의 본 실험과 최종 보고는 이후 단계다. A0가 B보다 높은 점수를 받아야만 완료되는 것은 아니다.

3. 확인된 문제와 변경 요구사항

ID 현재 확인된 상황 바꿀 것 완료 증거
C01 주식수 합계가 기존주식+신주+희석주식의 고정 3항이다. 멜콘 의무인수 누락, DTS 옵션 오가산·추가인수 누락이 발생했다. 주식수 구성과 분모 포함 여부를 별도 표현한다. 구성별 입력·합계·적용 분모와 합성 검증
C02 직접 시가총액이 없으면 기준주가·주식수가 있어도 계산기에 전달할 수 없다. 공시값·파생값·미확인을 구분하고 출처를 보존한다. 파생 계산 경로·단위·기간·원입력 근거
C03 다섯 고정 검색의 선택 쪽에 없는 사실을 추가 정보 요청으로 남겼다. B의 고정 조회 범위를 보완하고 A0에 같은 코퍼스 재조회 기능을 준다. 검색/열람/미확인의 구분, 새 조회 기록
C04 최종 서술과 계산 첨부의 사용 관계가 명시적이지 않다. 구조화된 계산 사용·배제와 값 참조를 출력에 연결한다. 계산 ID와 수치 일치, 배제 이유
A01 실행 ID·condition·actor와 실행 흐름이 B에 고정돼 있다. 공통 실행기 위에 B 정책과 A0 정책을 나눈다. 조건에 맞는 식별·로그·같은 도구/제한
A02 A0의 반복·컨텍스트·종료·실패 계약이 없다. 허용 도구 루프, 예산 예약, 제출·중단 규칙을 만든다. 모의 실행과 실제 개발 실행의 전 과정
E01 세 파일럿은 개발 중 본 사례다. 개발/최종 평가 배정을 먼저 기록한다. 배정표·버전·포함/제외 이유

현재 멜콘은 사실 5/5·계산 2/3, DTS는 사실 4/5·계산 3/3이다. DTS는 잘못된 자동 합계를 명시적으로 배제해 계산 K1을 인정받았다. 세 사례의 J1~J4 각 2점은 전체 정답률 100%를 뜻하지 않는다. HDMS의 과거 설정과 신규 두 기업 설정도 다르므로 현재 점수로 통제 비교를 주장하지 않는다.

4. 공통 보완과 A1의 경계

모든 조건에 공통 적용 W11의 A1 후보로 남길 것
구성 수량·포함 표시에 따른 정확한 산술 원문을 해석해 포함/제외 판단이 적절한지 자동 판정
직접값/파생값/단위/근거를 보존하는 데이터 계약 정정 전후 혼동 등 관찰된 실패를 탐지해 추가 재조회 지시
필수 필드·허용 ID·계산 참조 값의 기계적 일치 자연어 결론과 원문·계산 사이 의미적 모순 판단
B의 사전 고정 조회, A0의 자율 조회에 같은 도구 제공 실패 신호에 따라 검토 초안을 다시 작성시키는 절차

공통 검사기는 “이 숫자가 공시상 올바른 선택인가”를 정답표로 판정하지 않는다. calc_id가 없거나 참조한 결과와 구조화된 숫자가 다른 경우는 형식·연결 오류로 반환한다. 문장 전체가 계산과 모순되는지 자동 이해하는 검사는 A0에 미리 붙이지 않는다. 형식수정은 전체 실행에서 한 번이며, 사실·결론을 고치거나 추가 검색할 기회로 쓰지 않는다.

6. 입력과 계산의 데이터 계약

6.1 값의 출처와 상태

모든 값은 고유 fact_id, 십진수 문자열 또는 null, unit, period, as_of, scope, origin, evidence, missing_reason을 가진다. 기존 claim_id는 주장 연결 ID로 유지한다. origin은 DISCLOSED, DERIVED, UNAVAILABLE, NOT_APPLICABLE이다. DERIVED에는 derivation_id가 필수다. 적용 불가와 미확인에는 이유를 적고 0으로 대체하지 않는다. 공시가 명시한 0은 DISCLOSED 값 "0"과 원문 근거를 가진다.

evidence는 기존 doc_id/chunk_id/page/claim_id/locator를 유지한다. 원문으로 확인한 사실은 실제 열람한 페이지에만 연결한다. 파생값은 허용 연산·입력 fact ID·입력 스냅샷·결과·상태를 갖고, 모든 원입력 근거를 끝까지 추적할 수 있어야 한다. 의존성 순환과 존재하지 않는 ID는 거부한다.

이익은 백만원, 시가총액은 백만원, 주가는 원, 주식수는 정수 주, PER은 배로 계산한다. 단위는 필드별 매핑으로 검사한다. 기존처럼 reported_price_krw만 예외 처리하면 새 비교기업 주가를 검사할 수 없으므로 함께 바꾼다. 기간·귀속 범위·연결/별도·정정 구획을 섞지 않았는지 확인할 자료를 저장하되, 프로그램이 원문의 경제적 적합성을 보증하지 않는다.

6.2 주식수 구성

share_components[]의 각 행은 아래를 가진다.

필드 규칙
component_id·fact_id 서로 구별되는 구성/수량 ID. 같은 행을 중복 합산하지 않는다.
kind EXISTING, PRIMARY_NEW, MANDATORY_UNDERWRITER, ADDITIONAL_UNDERWRITER, OPTION, SECONDARY_SALE, OTHER_DILUTION
quantity 0 이상 정수 문자열 또는 미확인 null, 6.1의 근거 연결
denominator_treatment INCLUDE, EXCLUDE, UNRESOLVED
treatment_reason·treatment_evidence 모델이 읽은 포함/제외 근거. 평가자 정답을 넣지 않는다.
snapshot_id·basis 같은 적용 시점·정정 구획·공모 전/후 기준을 식별한다.

분모 구성은 공모 전 기발행 주식에서 출발해 서로 겹치지 않는 증가분을 더한다. 이미 공모 후 합계인 값을 기발행 구성으로 넣고 신주를 다시 더하지 않는다. 프로그램은 명시된 basis·ID·스냅샷의 계약을 검사하며, 실제 원문 독해가 틀렸는지는 채점한다. 동일한 시점이라도 서로 다른 출처를 쓰는 것은 허용하되 같은 적용 기준임을 명시한다.

합계는 INCLUDE 구성만 더한다. 완전한 derived_share_count를 반환하려면 모델 선언 coverage_status=COMPLETE, 모든 분모 관련 적용 여부 해결, 필요한 INCLUDE 구성 수량 확인을 모두 충족해야 한다. INCOMPLETE이거나 필요한 적용 여부/수량이 미확인이면 완전 합계는 null이며, 확인한 부분만 partial_sum으로 반환한다. 분모와 무관하게 EXCLUDE인 구주 수량 null은 그 자체로 분모 산술을 막지 않고 사실 미확인으로 남긴다. 구주는 발행주식수 증가분에 더하지 않으며, 옵션의 포함 여부는 공시의 적용 분모에 대한 모델 입력으로 결정한다. 옵션이라는 이유만으로 자동 포함하지 않는다. coverage_status에는 모델이 읽은 근거/한계를 붙인다. 계산기의 OK는 입력에 대한 산술 성공이며 완전성 선언이 맞다는 정답 판정이 아니다.

직접 공시된 reported_share_count와 구성으로 구한 derived_share_count를 따로 보관한다. selected_share_count에는 선택한 값의 ID와 이유를 적는다. 둘이 다르면 차이 계산을 보여주고 자동 덮어쓰지 않는다. 사용하지 않은 계산도 지우지 않는다.

6.3 파생값과 계산 가능성

비교기업에는 기존 PER·직접 시가총액·이익 외에 reference_price_krw, reference_shares, 기준일/평균 산정 방식·회사 범위를 표현하는 원입력을 추가한다. 허용되는 파생식은 다음과 같이 코드로 정한다. 임의 Python·문자열 eval은 받지 않는다.

시가총액(백만원) = 기준주가(원) × 해당 기준 주식수(주) ÷ 1,000,000
재계산 PER = 선택한 시가총액(백만원) ÷ 해당 기간 이익(백만원)
주당 평가액(원) = 선택한 주식가치(백만원) × 1,000,000 ÷ 선택한 분모(주)

직접 시가총액과 파생 시가총액이 함께 있으면 둘 다 유지하고 선택 이유를 기록한다. 수치 차이를 숨기거나 임의 평균하지 않는다. 날짜·주식 기준이 양립하지 않거나 이익이 양수가 아니어서 현재 PER 계산 범위를 벗어나면 계산 불가 이유를 반환한다. 다른 방법으로 임의 전환하지 않는다. 표시 배수·정밀도 차이는 공시 오류로 자동 판정하지 않는다.

필드에는 원공시 존재 상태와 업무상 사용 가능 상태를 함께 둔다. 사용 가능 상태는 DIRECT, DERIVABLE, UNRESOLVED, NOT_APPLICABLE이다. 직접 시가총액이 없지만 유효한 원입력으로 파생 가능하면 DERIVABLE이며, 직접값 부재만으로 외부 요청을 강제하지 않는다. missing_inputs는 업무 수행에 남은 UNRESOLVED 의존성에만 연결한다. 단순히 모든 null 필드와 정확히 일치시키는 현재 규칙을 바꾼다. 적용 불가와 원공시 미기재도 별도 범위 설명에 남긴다.

6.4 계산 결과와 최종 사용 연결

모든 계산은 calc_id, input_snapshot_id, 입력 fact ID, 식, 결과, 단위, OK/UNAVAILABLE/INVALID, 이유를 가진다. review_v2.calculation_uses[]는 calc_id, USE/REJECT, stated_value, 관련 판단 ID, 이유를 가진다. USE의 stated_value는 해당 결과와 같아야 한다. REJECT는 이유와 대신 사용한 계산/값 ID 또는 아직 미해결임을 표시한다.

사람이 보는 계산 첨부는 이 레코드에서 생성한다. 수치 일치는 유한 Decimal 값의 동등성으로 검사하므로 10, 10.0은 같은 수다. 저장 형식은 정규화한 십진수 문자열을 사용하고 비교 허용 오차를 임의 추가하지 않는다. 계산 입력이 변경되면 스냅샷 ID도 바뀌며, 예전 계산을 새 입력의 결과로 제출할 수 없다. 자연어 문장의 모든 숫자를 자동 이해해 교정한다고 주장하지 않는다. 예전 계산의 명시적 배제는 허용하고, 배제했다고 원래 계산을 삭제하지 않는다.

6.5 작은 묶음의 등록과 사용 가능 상태

A0에 전체 추출 JSON을 탐색 한 번에 생성하도록 요구하지 않는다. calculate는 공통으로 REGISTER_BATCH와 EVALUATE 두 operation을 지원한다. 전자는 base_snapshot_id, records[], 후자는 input_snapshot_id, 허용 calculation_types[]를 받는다. records는 VALUE, SHARE_COMPONENT, PEER, DERIVATION, SELECTION, COVERAGE, CONTEXT의 자료형별 계약을 가진다. 같은 record ID의 수정은 새 버전으로 등록한다. VALUE가 참조하는 단위·기간·기준일·범위는 CONTEXT ID로 공유할 수 있고, 저장된 완전 논리 FACT에서는 6.1의 필드로 해석한다. 원문 evidence도 검증된 ID로 참조해 같은 긴 내용을 매번 출력하지 않는다.

게이트웨이는 각 묶음을 원자적으로 검사하고 새로운 불변 snapshot ID와 등록한 ID 목록만 반환한다. 불완전 등록 상태는 허용하지만 미등록 필드를 0이나 공시 부재로 채우지 않는다. 아직 필요한 레코드가 없으면 EVALUATE는 부분합/UNAVAILABLE과 부족 ID를 반환한다. B도 동일 계약에 기존 추출 호출의 결과를 묶음으로 등록한다. 각 등록과 계산은 실제 도구 호출로 세므로 A0의 비용을 숨기지 않는다. 필요한 자료가 5,000 탐색 출력 총예산 안에 등록되지 않으면 정상적인 예산 한계로 기록한다.

전송 형식은 operation별 strict 스키마 하나를 선택해 검증한다. RECORD의 payload에는 해당 자료형의 필수 키만 허용하며, 한 호출의 묶음 크기는 생성 가능한 탐색 출력 한도 안으로 제한한다. 논리 스냅샷 전체는 프로그램이 조립해 저장한다. COMMIT은 전체 추출값을 모델이 다시 출력하는 대신 snapshot ID를 참조한다.

원공시 상태 필드는 disclosure_status=PRESENT/NOT_FOUND/NOT_APPLICABLE, 업무 상태는 usability=DIRECT/DERIVABLE/UNRESOLVED/NOT_APPLICABLE로 정한다. NOT_FOUND는 확인한 범위에서 못 찾았다는 뜻이며 문서 전체 부재 판정이 아니다. 아래 합성 예제는 직접 공시값을 찾지 못해도 파생값을 선택할 수 있음을 보여준다. 실제 FACT와 DERIVATION 레코드는 각 ID로 별도 보존한다.

{
  "field": "peer_market_cap_million_krw",
  "disclosed_fact_id": "F_SYN_CAP_NOT_FOUND",
  "disclosure_status": "NOT_FOUND",
  "usability": "DERIVABLE",
  "selected_fact_id": "D_SYN_CAP_100000",
  "selection_reason": "같은 기준의 주가와 주식수로 파생 계산"
}

7. 검색과 열람 설계

7.1 모든 조건의 공통 경계

등록 사례의 공개 코퍼스만 조회한다. 모델이 사례 경로, 사적 기준표, 다른 실행 답변, 웹 URL이나 shell 명령을 지정할 수 없다. case_id와 허용 문서는 실행기가 고정한다. 페이지는 물리 PDF 쪽과 인쇄 쪽을 구별한다.

게이트웨이 초깃값은 검색 top_k=1~3, 질의 1~300자, 열람 chunk ID 1~3개, neighbor_pages=0~1이다. 검색 필터는 등록 허용 목록 안의 doc_id와 실행기가 고정한 cutoff_status=BEFORE만 허용한다. 다른 키와 자료 마감 이후 조건은 거부한다. 모든 정수에는 bool·음수·분수를 허용하지 않는다. 한 번 열람은 중복 제거 후 최대 9쪽이며, 초과하면 TOO_LARGE와 허용 크기를 반환한다. 페이지는 전체를 반환하고 조용히 자르지 않는다. 큰 한 쪽이 요청 예산에 맞지 않아도 몰래 자르지 않고 명시적 예산 오류로 남긴다. 이 값들은 새 개발 버전의 공통 설정이며 최종 평가 전 동결한다.

검색 발췌는 발견을 돕는 일부 텍스트다. search_hits와 read_chunks를 따로 기록하고, 최종 인용은 read_source로 실제 받은 페이지에 한정한다. 같은 페이지를 다시 읽는 것은 허용하되 재조회도 호출에 계상한다.

7.2 B의 고정 조회 보완

현재 다섯 검색은 유지하고, 다음 세 검색을 모든 개발 기업에 같은 순서로 추가하는 초안을 시험한다.

  1. 인수인 의무인수 추가인수 주식매수선택권 구주매출
  2. 기준주가 종가 평균주가 발행주식수 시가총액
  3. 최근 12개월 연환산 금융수익 금융비용 매출구성

각 검색은 상위 3쪽과 앞뒤 한 쪽을 읽고 합친다. 기업별 정답 페이지나 수치를 검색 지시문에 하드코딩하지 않는다. 총 8회 검색+8회 열람, 추출 등록 1회, 계산·민감도 2회, 요청·이관 2회, 제출 1회이면 정상 경로 도구는 22회다. 겹치는 페이지는 한 번만 본문 패킷에 담는다.

최대 72쪽 후보가 생길 수 있으므로 무료 점검에서 누적 입력·출력·비용 예약까지 확인한다. 기존 16만 입력 목표로 맞지 않으면 해당 계획을 PREFLIGHT_BLOCKED_BUDGET로 표시하고 실제 호출을 시작하지 않는다. 답을 보기 전에 공통 조회 정책이나 예산을 새 버전으로 조정하고 이유를 남긴다. 특정 기업의 정답을 알고 유리한 쪽만 골라 줄이지 않는다.

7.3 A0의 재조회와 미확인 이유

A0는 같은 검색·열람 기능에서 질의와 다음 순서를 고른다. B의 선택 페이지나 이전 답변을 A0 초기값으로 전달하지 않는다. 문서 목록·자료 마감·공통 방법서·업무·도구 계약으로 시작하고, 실제 받은 결과를 같은 실행 안에서 누적한다.

미확인은 NOT_READ(아직 열람하지 않음), SEARCH_NOT_FOUND(시도했지만 못 찾음), UNAVAILABLE_IN_ALLOWED_INPUT(확인한 허용 자료의 한계), BUDGET_LIMIT로 나눈다. 이 분류도 모델의 주장과 실제 조회 이력을 나란히 저장한다. “못 찾음”을 전체 문서에 없다는 증거로 취급하지 않는다. 내부 원문으로 해결할 수 있는 질문과 외부 자료가 필요한 요청을 구분해 기록한다.

탐색에서 사용하는 제출 의도 인자의 예시는 아래와 같다. 아직 최종 보고서 본문을 만들지 않는다.

{"phase":"PREPARE","input_snapshot_id":"X_SYNTH_001"}

실행기는 현재 단계에 맞는 submit_review 스키마 하나만 노출한다. 탐색에서는 PREPARE 인자만, 최종화에서는 COMMIT과 전체 제출 계약만 허용한다. 따라서 탐색 응답 한도 안에서 긴 최종 JSON을 작성하다 잘리는 흐름을 피한다. 이 예시는 합성 ID이며 실제 정답 입력이 아니다.

8.2 행동과 컨텍스트

Responses API의 function calling으로 모델이 도구를 선택하고 프로그램이 실행 결과를 돌려주는 루프를 사용한다. 함수 스키마는 strict: true, 객체는 additionalProperties: false, 필수 키를 명시한다. 순서를 한 행동씩 관찰하기 위해 parallel_tool_calls=false로 설계한다. API가 반환한 도구 호출과 결과는 call_id로 연결하고, 같은 실행의 응답 항목과 필요한 reasoning 항목을 다음 요청에 보존한다. OpenAI function calling 공식 문서

최종 문서의 구조화 출력과 거부·불완전 응답 처리는 별도로 확인한다. 스키마에 맞는 응답도 사실의 정확성을 보증하지 않는다. OpenAI structured outputs 공식 문서

이 선택은 이번 설계의 구현 방침이다. 현재 코드의 Run.call()은 response.output_text를 JSON으로 읽으므로, 기존 메서드를 그대로 재사용해 function call을 읽었다고 하지 않는다. 공통 요청·사용량 기록은 재사용하고 도구 응답 파싱 경로를 분리한다. 계정·현재 모델과 SDK의 도구 호출 호환성은 구현 후 작은 연결 점검으로 확인하며 모델을 몰래 바꾸지 않는다.

실행마다 새로운 컨텍스트를 만든다. 다른 기업·조건·반복의 응답이나 채점표는 넣지 않는다. 전체 도구 이력과 실제 받은 페이지를 누적하며, 입력량은 매 호출의 전체 전송분으로 계산한다. 첫 버전은 자동 요약이나 숨은 메모리 압축을 하지 않는다. 같은 원문이 여러 호출에 실리면 그 사용량도 누적한다. 예산이 부족하면 종료 규칙을 적용한다.

8.3 상태와 종료

CREATED → INPUT_VERIFIED → PREFLIGHT_COMPLETE
  ├─ 실제 실행 안 함: PREFLIGHT_COMPLETE로 종료
  ├─ 키 없음: NOT_STARTED_MISSING_API_KEY로 종료
  └─ 실제 실행: EXPLORING ↔ 도구 관찰
                    → FINALIZING → SUBMITTED
                    → FAILED (거부·형식 실패·예산·시간·도구 경계 위반 등)

모델이 submit_review(PREPARE)를 선택하거나, 다음 탐색 요청이 예약 예산을 침범하면 최종화로 넘어간다. PREPARE도 탐색 도구 한 번으로 계상한다. 다음 모델 호출에서 COMMIT만 선택할 수 있게 하고 예약된 최종 출력 8,500을 사용한다. 최종화에서는 추가 검색·계산·추출 스냅샷 수정을 허용하지 않고, 이미 얻은 사실·계산·미확인으로 검토 의견과 새 정보 요청/이관을 작성한다. 사용할 새 계산이 꼭 필요하면 탐색 단계에서 해야 한다. 유효한 제출을 만들 수 없으면 실패를 보존한다.

요청·이관은 ID별 이력을 보존한다. 동일 ID 재등록은 멱등 처리하고, 기존 OPEN 항목을 최종 목록에서 빠뜨려 없앨 수 없다. 취소/비차단 변경은 이유와 새 버전을 기록한다. RESOLVED는 실제 열람한 허용 원문의 해결 근거가 있을 때만 가능하다. 최종 내용 상태는 모델이 보낸 마지막 목록만이 아니라 이 동기화된 전체 요청/이관 원장으로 계산한다.

모델이 도구 호출 없이 끝냈는데 유효 제출이 없으면 NO_VALID_SUBMISSION이다. 거부·불완전 응답, API 오류, 사용량 누락은 이유를 분리하고 임의 재호출하지 않는다. JSON 형식·필수 필드·ID 연결 오류는 기존 공통 형식수정 1회에 포함하며, 등록·최종 제출을 합쳐 이미 사용했으면 종료한다. 수량·판단·근거 사실을 새로 고치는 용도로 형식수정을 쓰지 않는다. 유효 인자로 실행한 검색의 0건, 계산 UNAVAILABLE, 큰 열람의 TOO_LARGE 등은 도구 관찰이며 A0는 예산 안에서 다음 행동을 고를 수 있다. 금지된 자료/경로 접근 시도는 반환 차단·기록하고 명시적 격리 위반으로 실행을 종료한다.

SUBMITTED는 실행 성공 여부다. 내용 상태는 별도로 READY, PENDING_INFO, HUMAN_REVIEW를 기존 final_status() 원칙에 따라 계산한다. 미해결 blocking 이관이 우선하고, 다음은 blocking 정보 요청이다. READY는 정답 승인이나 투자 판단 승인이 아니다. 무효 제출의 내용 상태는 null이며 실패 이유가 별도다.

9. 예산과 예약

다음 숫자는 현재 config/B.json에서 확인한 개발 기준이다. 새 버전에서 B와 A0 모두 같은 상한을 적용한다. 최종 평가 전에는 실제 사용량으로 전체 약 10만원 목표를 다시 산정한다. 아래 단가와 환산값은 현재 프로젝트 설정이며 새로운 요금 견적이 아니다.

항목 개발 기준 처리
모델·추론 gpt-6.1-terra / medium B/A0 동일, 실제 반환 모델과 SDK 기록
모델 호출 16회 탐색 전에 최종화 1회+형식수정 1회 예약
도구 호출 40회 최종 요청·이관 동기화 2회+제출 1회+형식수정 후 재제출 1회 예약
누적 입력 목표 160,000토큰 이전 프로토콜의 120,000은 초기값. 매 호출 전체 입력을 추정하고 실제값 누적
누적 출력 16,000토큰 최종 8,500+형식수정 2,500 예약, 탐색 최대 여유 5,000

실행 비용 0.30달러 모든 호출·형식수정 포함. 일반 입력 1달러/백만·출력 5달러/백만의 현 설정으로 예산 검사
형식수정 전체 1회 입력 16,000·출력 2,500 예약. 사실 재검토 allowance가 아님
예산 환산 달러당 1,400원 청구서 금액과 구분, 캐시 반영 사후 비용 별도

도구 예약 4회는 새 A0의 구현 설계다. 최종화에서 두 요청 목록을 실제로 등록/동기화하고 호출로 계상한다. 탐색 중 같은 요청을 이미 기록했다면 ID로 중복 생성하지 않되 동기화 호출 비용은 센다. 형식수정 후 재제출을 쓰지 않으면 예약을 소비하지 않는다. 예약은 동기화 2회+COMMIT 1회+수정 후 COMMIT 1회에 쓰며 PREPARE는 탐색 예산에서 지불한다. COMMIT 인자를 받으면 예약된 동기화 뒤 실제 제출 검증을 수행한다.

새 탐색 호출은 모델/도구 수뿐 아니라 입력·출력·돈·시간 여유를 함께 검사한다. A0 탐색 출력 상한은 min(1000, 16000 - 실제누적출력 - 11000)이며 0 이하면 최종화한다. 1,000은 새 개발 설정이며 실제 소비량만 누적한다.

입력 예약은 고정 16,000만으로 충분하다고 가정하지 않는다. 현재 누적 이력+최종 스키마+예정된 도구 결과 상한을 포함한 최종 요청 추정치와 형식수정 입력 16,000을 예약한다. 단가 설정으로 이 두 요청의 비용도 먼저 빼고 탐색 여부를 결정한다. 다음 검색/열람이 가져올 최대 허용 페이지를 포함해 예약할 수 없으면 실행하지 않는다. 시간은 개발 초깃값으로 최종화 120초+형식수정 60초를 남기며, 실제 완료를 보장하는 값으로 해석하지 않는다. 준비 지연 등으로 여유가 사라지면 실패 사유를 남긴다.

최종 예산 검사에서도 넘으면 호출하지 않고 종료한다. 실제 사용량이 예측 상한을 넘은 경우 원본 usage와 초과 사실을 남긴다. 네트워크/API 실패로 사용량을 모르는 요청은 usage_unknown=true이며 0원으로 합산하지 않는다. 현재 개발 API 클라이언트의 max_retries=0을 유지하고 새 개발 실행은 새 ID와 이유를 남긴다. 프로토콜의 ‘실행 시작 전 확인된 일시적 통신 장애 동일 요청 최대 2회’는 허용 상한이며 재시도 의무가 아니다. 그 예외를 채택하려면 실행 시작/과금 여부·동일 요청·모든 시도 비용을 추적할 별도 사전 정책이 필요하다. 모델 답변을 본 뒤 재실행해 좋은 결과만 채택하는 규칙으로 확대하지 않는다.

10. 사례 확대와 개발 비교

먼저 공개자료의 버전·자료 마감·실적 PER 적격성·비금융 여부를 확인하고 포함/제외 이유를 남긴다. 배정은 기업 단위다. 동일 기업의 다른 문서나 반복 답변이 개발과 평가에 나뉘어 들어가지 않게 한다. 정답 기준표는 모델 입력과 분리한다.

안 개발 기업 추가 개발 평가 기업 최종 평가 실행
기본안 10 현재 3+추가 7 20 20×3조건×2회=120
축소안 6 현재 3+추가 3 12 12×3조건×2회=72

세 파일럿은 개발용으로 고정한다. 최종 규모는 W12 이전에 실제 적격 사례와 작업량을 보고 결정한다. 개발 실행은 최종 120/72회에 포함하지 않는다. 후보 모집·공개 입력 준비와 공통 코드 개발은 병행할 수 있다. 평가 기업의 답변은 W12 동결 이후에 받는다.

새 공통 버전의 B와 A0를 개발 사례마다 우선 한 번씩 실행하는 개발 비교표를 작성한다. 현재 3기업만 비교하는 첫 묶음은 3×2=6회이며, 이는 기능 점검과 실패 수집용이다. 추가 개발 기업도 같은 기준을 적용하고, 실제 반복/수정 실행은 별도 행으로 기록한다. 사전 조건과 원본 usage를 남기고 이전 R001 점수를 새 B 점수로 대신 쓰지 않는다.

채점표에는 사실 F·계산 K·J1~J4, 출처 적합성, 잘못된 완료, 불필요한 보류, API 비용·경과 시간을 둔다. 현재 수행 가능한 AI 보조 채점과 규리의 직접 검토 여부를 각각 기록한다. 독립 사람 채점이 이미 끝났다고 표시하지 않고, 추가 외부 평가자 확보를 이 개발 단계의 조건으로 붙이지 않는다. 사람 작업시간은 측정한 경우만 별도 입력한다.

실패 레코드는 failure_id, 사례/조건/실행, 관찰한 도구·페이지·입력·계산 ID, 실패 유형, 실제 문제, 점수 영향, A1 탐지 후보, 예상 재검토, 추가 비용을 가진다. 우선순위는 검토 결론에 미치는 영향·재발 여부·탐지 가능성으로 정한다. A1의 각 장치는 한 개 이상의 실제로 관찰한 A0 실패와 연결한다. B 파일럿에서 본 문제만으로 A1 효과를 확정하지 않는다.

T09 직접값 null이지만 유효 파생값 존재 DERIVABLE. 직접값 부재만으로 blocking 외부 요청을 만들지 않음
T10 의존성 순환, 모르는 fact/calc ID, 새 추출에 옛 계산 사용 거부. 원입력 근거를 추적할 수 없는 값은 제출 불가
T11 검색 발췌만 보고 인용, 다른 사례 ID/사적 경로/범위 밖 페이지 인용 또는 접근 거부. 실제 읽은 허용 원문만 인용 가능
T12 3개 chunk와 이웃 쪽, 중복·최대량 초과 중복 제거·전체 페이지 반환, 9쪽 초과는 명시 오류
T13 남은 출력 11,000, 모델 2회, 도구 4회만 남음 새 탐색을 시작하지 않고 최종화 예약 보존
T14 최종 입력+형식수정 예약 또는 돈/시간 부족 호출 전 차단. 한도 초과를 감추지 않음
T15 모의 A0가 검색→열람→작은 레코드 등록→계산→재검색→PREPARE→COMMIT 선택 작은 등록과 최종화가 각 출력 예약 안에서 작동하고 실제 모델 선택 순서를 기록
T16 도구 없는 종료, API 거부/불완전/사용량 누락, 형식수정 2회 요구 사유별 실패 보존. 미확인 사용량을 0으로 집계하지 않음
T17 blocking 요청/이관과 유효 제출, 또는 무효 제출 PENDING_INFO/HUMAN_REVIEW 우선순위 유지. 무효 제출은 내용 상태 null
T18 새 실행·다른 조건·다른 반복 시작 직전 답변·도구 이력·비공개 기준표가 초기 입력에 없음
T19 계산 사용 레코드 값과 calc 결과 불일치, 또는 명시적 REJECT 불일치는 형식 오류. 근거 있는 배제는 원계산 보존하며 표현 가능
T20 정상 원문을 받은 A0가 잘못된 포함 여부/자연어 결론을 씀 공통층이 정답으로 고쳐 주지 않음. 실제 실패로 채점·A1 후보화

기존 회귀 146개는 과거 파일럿의 검증 수다. 새 개발 후에는 실제로 수집된 테스트 수와 결과를 기록하며 무조건 같은 수를 유지했다고 적지 않는다. 합성 검증 통과와 실제 모델 성능 개선도 따로 보고한다.

13. 실행 기록·보존·인계 산출물

기존 runs/<run_id>/의 설정·환경·입력 해시·원본 요청/응답·계산·review·summary·events를 유지한다. 새 버전에서는 조건·반복·계약 버전·input snapshot·선택 actor(program_fixed, model, program_commit)·도구 call ID·실패 사유·예약/누적 예산·읽은 쪽을 추가한다. 내부 회계 검사로 모델의 행동을 위장하지 않는다.

새 산출물은 다음과 같이 구분한다. 이름은 구현 시 실제 실행 ID와 연결해 확정한다.

  • 공통 보완 명세와 구현 변경 기록, 원본 보존 검사 결과.
  • v2 계약 예제·합성/회귀 결과, 무료 점검 결과.
  • 신규 config/A0.json, A0 정책·도구 계약·공통 설정 비교표.
  • 개발/평가 사례 배정표, 공개 입력과 비공개 기준표의 버전·해시.
  • 새 B/A0 개발 실행 목록, 답변 또는 실패, 호출/페이지/시간/비용, 채점 사유.
  • failure_id → 관찰 근거 → A1 후보 → 재검토 → 추가 비용 인계표.

기존 R001 실행·점수·기준표와 과거 코드/설정 스냅샷은 보존한다. 현재 작업 코드의 수정은 새 버전·커밋과 새 실행으로 남긴다. 과거 파일의 해시와 새 코드 해시가 달라지는 것은 버전 변경으로 설명하며, 과거 실행을 새 코드로 실행한 것으로 바꾸지 않는다. 기준표 수정이 필요하면 사유·시점·버전을 남기고 기존 점수를 소급 덮어쓰지 않는다.

14. 아직 고정하지 않은 항목과 다음 한 작업

새 공통 버전의 검색 3개·게이트웨이 한도·탐색 출력 1,000·시간 예약 120+60초는 개발 초깃값이다. 무료 점검과 개발 실행을 근거로 조정할 수 있으며 B/A0의 공통 접근 조건을 맞춘다. 최종 모델 snapshot, 표본 규모, 전체 비용 재산정, 최종 채점 방식과 사람 작업시간 측정은 W12 이전에 확정한다. 결과가 유리한 방향으로 나온 뒤 최종 평가 기준을 바꾸지 않는다.

바로 시작할 일은 D0 보존 목록을 확인하고 D1의 주식수 구성·파생값·계산 참조 계약을 코드와 합성 입력으로 만드는 것이다. 그다음 D2 계산기, D3 공통 도구/조회/예산, D4 A0 루프 순서로 간다. 실제 구현·실행 후에는 이 문서의 예정 상태를 근거 파일과 함께 갱신한다.
