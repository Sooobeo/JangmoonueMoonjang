# 상세계획 문서의 세 차례 자가점검

- 점검일: 2026-11-12, 한국시간
- 대상: [IPO_후속작업_상세계획.md](../../whole%20plan/IPO_후속작업_상세계획.md)
- 담당 범위: 상세계획의 표현과 맥락을 개정하고 이 점검 기록을 작성했다. 이 담당 작업에서 다른 코드·자료·Phase 1 원문은 수정하지 않았다.
- 요청한 세 관점: 내용의 정확성, 기존 계획과의 일치, 일반 독자가 앞뒤 사정을 이해할 수 있는지.
- 주의: 문서의 세 차례 자가점검은 구현 전체의 검증이나 규리의 답변 채점을 대신하지 않는다. 프로그램 각 단계의 점검은 해당 담당 기록에서 확인한다.
- 최신 상태: 키 교체와 개발 중 실패 수정을 거쳐 실제 Terra의 유효 제출 한 편을 확보했다. 아래 1~5절은 당시 점검과 변경 이력이며, 최종 제출 뒤의 확인은 6절에 추가했다.

## 1. 개정에서 바꾼 점

기존 문서는 할 일과 결과물을 잘 나누었지만, 짧은 명사와 프로그램 용어만 이어지는 부분이 있었다. 이번에는 먼저 프로젝트가 무엇을 하려는지 설명하고, 왜 원문을 모으고 검색·계산 기능을 만든 뒤 모델을 연결하는지 순서대로 풀었다.

W01~W14는 모두 남겼다. 이번 요청은 W01~W06의 HDMS 첫 B 실행까지이며, W07~W14의 규리 채점·사례 추가·A0/A1·최종 비교는 이후 예정으로 분리했다. 각 단계에는 앞 단계와의 연결, 제가 하는 일, 남길 결과와 다음 단계로 넘어갈 기준을 적었다.

API, 토큰, 파일 확인값인 SHA-256, 정해진 항목으로 저장하는 JSON, 난수 시작값, 코드 버전 번호, 기업을 다시 뽑는 비교 방법을 일상적인 표현으로 설명했다. 함수명과 저장 항목명은 실제 구현을 연결할 수 있도록 보존하고 바로 옆에 한국어 뜻을 적었다.

문서가 계획하는 작업과 실제 완료된 작업도 구분했다. 원문 준비와 B 작성·모의 점검을 진행했어도 API 연결이 준비되지 않아 실제 Terra 답변은 없다는 상태를 상단과 진행 상태 표에 남겼다.

## 2. 1차 점검: 숫자와 설명이 맞는가

- 공시의 실제 숫자 예시는 모델 실행의 정답 힌트로 넣지 않는다는 설명을 확인했다.
- 2026-11-11에 확인한 단가를 이용한 예산 계산과, 실제 호출 때 요금을 다시 확인한다는 조건을 구분했다.

### 결과

문서에 제시한 계산과 예산 산식은 맞는다. 단가·환율·개발 실행 횟수는 실제 지출을 보장하는 값이 아니라 예산 가정이라는 조건을 남겼다. 이 문서 점검으로 실제 API 사용량이나 모델 성능을 확인했다고 표시하지 않았다.

실험 프로토콜의 8.2~8.6, 9.2, 11.1, 12.1 내용을 문서의 W04~W14와 평가 설명에 대조했다.

### 이 점검 뒤 보완한 부분

- 공시 안의 명령처럼 보이는 문장은 분석 자료이며 실행 지시를 바꾸지 않는다는 설명을 추가했다.
- 검사기의 탐지율은 그 검사기가 원래 대상으로 삼은 오류를 기준으로 계산한다고 명시했다.
- 배정·실행 순서의 난수 시작값과 모델 답변의 동일성 보장은 별개라고 설명했다.
- 조건부 수용도 중요한 미해결 정보에 의존하면 해당 요청이 완료를 막는다는 사실을 표시하도록 명시했다.
- 반복 간 상태·점수 변동과 자료 특성별 탐색적 결과를 따로 남기도록 보완했다.
- 예산 때문에 중단되면 미실행 목록과 이유를 남기고 전체 평가 완료로 표현하지 않는다고 적었다.

### 결과

연구 범위, 비교 조건, 비용 목표, 규리의 역할과 결과 해석 범위를 보존했다. 세 차례의 개발자 자가점검을 A1의 두 차례 수정이나 독립 평가자 추가로 혼동하지 않게 설명했다.

## 4. 3차 점검: 처음 읽는 사람도 이해할 수 있는가

문서를 앞에서부터 다시 읽고, 설명되지 않은 용어 때문에 다음 문장을 이해하기 어려운 부분을 찾았다. 개별 할 일만 남아 앞뒤 이유가 끊기지 않는지도 확인했다.

### 이 점검 뒤 고친 부분

- '배수'는 '몇 배라는 값'으로 설명하고, PER에 적용하는 이익은 적용 순이익이라고 구체화했다.
- 신조선 건조를 '새 선박을 만드는 사업'으로 풀었다.
- 대안 계산의 목적을 먼저 설명하고 평균과 중앙값, 짝수 개일 때의 중앙값을 설명했다.
- SPAC와 REIT의 한국어 이름을 붙이고, 다른 가치평가 방법을 핵심 범위에서 분리하는 이유를 적었다.
- '커밋'을 코드 변경 버전 번호로 설명했다.
- '복원추출'만 적는 대신 같은 기업이 여러 번 뽑힐 수 있도록 묶음을 다시 선택한다고 풀었다.
- '실패와 핵심 오류의 합집합'은 두 조건에 모두 해당해도 한 번만 센다는 표현으로 바꾸었다.
- 자료 폴더와 설정 파일은 각각 어디에 쓰는지 설명하고, 예정 구조와 실제 구현 파일의 이름이 다를 수 있음을 알렸다.
- 모든 실행 완료 판단은 실제 응답과 기록을 근거로 한다는 점을 다시 확인했다.

### 3차 점검 당시의 실행 상태 대조

첫 점검을 작성할 때 다음 실행 요약을 읽고 당시 상단의 상태 설명과 맞는지 확인했다. 이후 인증 시도의 상태 변경은 5절에 추가했다.

- [연결 전 점검 요약](../runs/20261111T230824Z_B_2da20d05/summary.json): `PREFLIGHT_COMPLETE`, `model_calls=0`, `actual_model_answer=false`.
- [실제 실행 시도 요약](../runs/20261111T231054Z_B_232f70d8/summary.json): `NOT_STARTED_MISSING_API_KEY`, `model_calls=0`, `final_status=null`, `actual_model_answer=false`.

실행 명령을 시도한 것과 모델을 실제 호출한 것을 구분했다. API 키가 없어 시작 전에 멈춘 상태를 FAILED 답변이나 READY 답변으로 새로 만들어 적지 않았다. 실제 답변이 없다는 점과 사용량 기준 비용이 0이라는 기록도 유지했다.

### 결과와 남은 확인

문서 개정에 대한 세 차례 자가점검을 마쳤다. 이해도 점검은 작성자가 일반 독자의 입장에서 다시 읽은 자가점검이며, 별도 독자 시험을 수행했다는 뜻은 아니다.

API 계정 접근, 실제 Terra 호출과 원본 답변, 그 답변의 내용·사용량·비용, 규리의 실제 채점은 이 문서 점검으로 완료되지 않았다. 그 결과가 생기면 [작업기록](작업기록.md)과 실행 파일을 근거로 상태를 갱신한다.

## 5. 추가 상태 확인: 키 등록 뒤 실제 요청의 인증 거부

2026-11-12에 사용자가 `.env`에 키를 등록한 뒤 실제 요청을 시도한 결과를 추가로 확인했다. 이 확인에서 키 값이나 `.env` 내용은 읽거나 문서에 기록하지 않았다.

- [실제 요청의 실행 요약](../runs/20261111T231508Z_B_8f5f6f03/summary.json)을 직접 읽었다. `mode=LIVE`, `execution_status=FAILED`, `model_calls=1`, `final_status=FAILED`, `actual_model_answer=false`이며 실패 이유는 `AuthenticationError`다.
- [작업기록](작업기록.md)에서 실제 Terra 요청이 `401 / invalid_api_key`로 거부됐고, 별도의 `GET /v1/models` 확인도 같은 결과였음을 확인했다. [인증 확인 기록](../runs/20261111T231508Z_B_8f5f6f03/authentication_check.json)이 연결되어 있다.
- 가장 최근 요약의 입력·출력 사용량은 0으로 기록되어 있지만 정상 응답의 사용량을 받지 못한 상태다. 이 값만으로 실제 청구 금액을 확정하지 않는다.
- 작업기록에는 현재 63개 테스트 통과가 기록되어 있다. 이는 프로그램과 모의 응답의 점검 결과이며 실제 Terra 답변의 검토 결과가 아니다.

상세계획 상단, 모델 연결 설명과 진행 상태 표를 이제 **키는 등록됐지만 인증이 거부되어 유효한 키로 교체를 기다리는 상태**로 고쳤다. 실제 답변 한 편이 생성됐다는 표시는 하지 않았다. 일반적인 절차를 설명한 '키가 없을 경우' 문장과 앞선 키 미등록 실행 기록은 당시 또는 조건부 설명으로 보존했다.

원래 실패 실행은 그대로 두고 유효한 키로 다시 시작할 때 새 실행 번호를 사용한다. 실제 답변 생성과 그 답변의 내용·출처·사용량 확인은 여전히 남아 있다.

## 6. 최종 제출 뒤의 추가 확인과 문서 상태 갱신

키 교체 뒤 인증을 통과했고, HDMS 개발 파일럿의 제출 구성을 보완해 `20261111T233807Z_B_2db53c6b`에서 실제 답변 한 편을 받았다. 이 추가 점검에서도 새 모델 호출을 하지 않았고 원본 응답과 실패 기록을 수정하지 않았다.

### 실제 산출물을 읽어 확인한 내용

- [최종 실행 요약](../runs/20261111T233807Z_B_2db53c6b/summary.json)은 SUBMITTED이고 `actual_model_answer=true`다.
- 추출·검토의 두 원본 API 응답은 모두 completed다. 각 응답을 파싱해 추출과 모델 작성 항목이 최종 저장 파일과 같은지 비교했다.
- [실제 답변 Markdown](../runs/20261111T233807Z_B_2db53c6b/review.md)과 [전체 JSON](../runs/20261111T233807Z_B_2db53c6b/review.json)이 존재한다.
- 구조 검사는 추출·검토 모두 오류 0개다. J1~J4 네 판단, 메모 5개, 정보 요청 2개가 있고, 요청은 모두 OPEN·blocking=false다. 사람 검토 요청은 없다.
- 프로그램과 모델의 상태는 READY로 일치한다. 이 상태는 규리의 정답 채점이 끝났다는 뜻이 아니다.
- 모델 요청 2회, 프로그램 기능 호출 15회, 입력 93,434토큰, 추론 포함 출력 10,554토큰, 형식수정 0회, 123.509초를 기록했다. 원본 사용량 합계가 요약과 같고 모두 공통 한도 안이다.
- 최종 JSON의 모델 작성 항목은 원본 검토 응답과 모두 같았다. 계산·대안 22개의 식·결과·단위·상태도 저장된 계산 기록과 같았다.
- 개발 실행 5개의 공개 자료 묶음 확인값은 같았다. 현재 Codex 대화, 정답 파일과 다른 실행의 추출 답안을 새 실험 입력으로 전달하지 않았는지 요청 구조와 입력 목록으로 확인했다.

자세한 독립 확인은 [형식·상태·실험 규칙 점검](review_protocol.md)에 남겼다. 실행·저장과 숫자·내용을 본 기록은 각각 [실행 점검](review_actual_run_execution.md), [계산·내용 점검](review_actual_run_calculations.md)에 있다.

### 상세계획에 갱신한 항목

문서 상단, 모델 접근 설명, 최신 출력 링크와 W01~W06 상태 표를 실제 제출 확보 상태로 고쳤다. W07 규리 채점과 그 이후 사례 추가·A0/A1·최종 평가는 미수행으로 남겼다. 향후 절차를 설명하는 일반적인 실패·인증·재시도 규칙은 유지했다.

개발 중에는 검토 출력 배분, 주장 ID 규칙, 중복 입력 전송, 메모·판단 개수의 형식 전달을 보완했다. 이는 최종 평가를 고정하기 전의 공통 실행·형식 수정이다. 각 실패와 원본은 [변경 기록](pilot_output_budget_change.md)과 실행 폴더에 그대로 남겼다.

비용 설명은 원본 요약의 일반 입력 가정과 캐시 읽기·쓰기를 반영한 [사용비용](사용비용.md)을 구분했다. 사용량이 확인된 금액은 유효 제출 1건 약 237.39원, 실패 요청까지 합쳐 약 983.27원의 추정이다. 사용량 미확인 인증 요청을 0원 청구로 단정하지 않았다.

전체 예산은 기존 250회 상당·입력 12만·출력 1.6만의 가정을 그대로 두었다. 일반 입력 가정의 7만원+예비비 3만원은 초기 단순 견적으로 남겼고, 모든 입력을 기본 30분 캐시에 쓴다고 보는 보수적 참고값 $0.23×1,400원×250=80,500원과 예비비 19,500원을 추가했다. 이 비용 계산으로 실행 횟수나 공통 자원 한도를 변경하지 않았다.

### 남아 있는 일

규리가 실제 답변을 채점하고 점수·판정 사유와 시간을 기록하는 W07은 다음 단계다. 이번 문서·코드·출력 점검을 그 채점이나 독립 전문가 검증으로 표현하지 않는다. 전체 프로젝트의 개발·평가 결과나 A1의 효과도 아직 측정하지 않았다.
