## 2. 첫 번째 점검: 실제 응답과 저장한 최종 답변이 같은가

### 원본과 형식

최종 실행의 `01_extract_response.json`과 `02_review_response.json`은 모두 `status=completed`이며, 반환 모델은 `gpt-6.1-terra`다. 추출 응답의 JSON은 저장된 `extraction.json`과 같았다.

검토 응답의 모델 작성 항목인 `scope`, `judgments`, `requests`, `escalations`, `missing_inputs`, `memo`, `model_reported_status`를 최종 `review.json`과 항목별로 비교했다. 모두 같았다. 프로그램이 별도로 붙인 실행 번호, 계산 기록과 최종 상태를 모델이 직접 작성한 것처럼 취급하지 않았다.

제공된 30개 문서 조각을 기준으로 구조 검사를 다시 실행했다.

| 확인 항목 | 결과 |
|---|---|
| 추출 형식·필수 항목·단위·근거 연결 | 오류 0개 |
| 최종 검토 형식과 ID·요청 연결 | 오류 0개 |
| 판단 영역 | J1, J2, J3, J4 순서로 정확히 4개 |
| 메모 | 5개 |
| 누락 계산 입력 | 없음 |
| 근거 문서 | 허용된 HDMS-PROS-01 안의 제공 위치 |
| 형식수정 | 0회 |
| 원본 모델 작성 내용과 최종 JSON | 모두 같음 |

이 구조 검사는 근거 위치와 주장 번호의 연결을 본다. 그 문장이 실제 사실을 올바르게 읽었는지, 판단 이유가 충분한지에 점수를 주는 검사는 아니다.

### 계산과 사람이 읽는 답변

최종 JSON에는 계산·대안 22개가 있다. 저장된 `calculations.json`의 각 계산과 대안을 기준으로 번호, 식, 결과, 단위와 상태를 비교해 차이가 없음을 확인했다. 번호도 중복되지 않았다. 각 계산에 입력의 단위·기간·출처가 함께 연결되어 있다.

Markdown에는 모델의 확인 범위, 메모, 각 판단의 결론·사실·미확인 사항·다음 행동이 모두 남아 있었다. 이 내용의 원문 문자열이 빠지지 않았는지 비교했다. 근거와 반대 근거를 읽을 수 있고, 요청과 계산 기록은 별도 항목에 있다.

## 3. 두 번째 점검: 상태와 요청을 정한 규칙대로 처리했는가

최종 답변의 정보 요청은 2개이며, 모두 `OPEN`이고 `blocking=false`다. 사람 검토 요청은 없다.

| 요청 | 남은 질문 | 실행 당시 표시 |
|---|---|---|
| REQ-01 | HD한국조선해양 순이익 두 수치의 차이를 설명하는 추가 허용 페이지가 있는가 | 현재 수치에 따른 제한적 검토 자체를 막지는 않는다고 설명 |
| REQ-02 | 미반올림 입력과 평가시가총액의 정확한 처리 규칙을 설명하는 추가 허용 페이지가 있는가 | 추가 대조를 위한 정보 요청으로 기록, 완료를 막는 표시 없음 |

따라서 프로그램의 구조적 판정은 READY다. 모델이 보고한 READY와 같고 `status_mismatch=false`다. 모든 판단이 CONDITIONAL이라고 해서 프로그램이 자동으로 보류 상태로 바꾸지는 않는다. 무엇이 완료를 막는지는 요청의 blocking 표시와 연결해 처리한다.

실제 실행 기록도 확인했다.

- `request_information`은 두 요청을 기록하고 `sent_externally=false`를 반환했다.
- `escalate`는 빈 목록을 기록했고 외부 전달은 없었다.
- `submit_review`는 `valid=true`와 `checks_factual_correctness=false`를 반환했다.

**READY는 정답 채점 완료나 투자 판단의 승인이라는 뜻이 아니다.** 두 요청을 완료를 막지 않는다고 본 판단이 적절했는지는 규리가 이후 평가할 항목이다. 요청을 실제로 회사에 보내거나 답변을 받아 해결한 것처럼 처리하지 않았다.

## 4. 세 번째 점검: B와 공통 실험 규칙을 지켰는가

### 정해 둔 순서와 같은 입력

행동 기록은 다섯 고정 검색과 각 원문 열람, 숫자 추출, 프로그램 계산·대안 계산, 검토 의견 작성, 요청 기록, 최종 제출 순서였다. 자료 조회·계산은 `actor=program_fixed`로 기록되어 있다. 모델이 중간에 새 검색을 계획하거나 다른 회사 자료를 추가로 찾은 실행이 아니다.

두 모델 요청에는 각각 system·user 메시지만 있었다. 이전 API 대화 번호나 현재 Codex 채팅을 전달하지 않았다. 첫 요청에는 공개 문서·공통 방법서·날짜와 사례 정보·추출 업무만 있었고, 검토 요청에는 그 실행에서 새로 받은 추출과 계산 결과가 더해졌다.

대상은 `HDMS-DEV-01`, 자료 마감은 `2024-04-24T23:59:59+09:00`이다. 제공 문서는 `HDMS-PROS-01` 하나이며 조회된 조각은 30개다. 원문과 공통 방법서를 담은 `source_packet.json`의 SHA-256은 개발 실행 5개에서 모두 같았다.

`e22db30ac5b2c1ccee5c6fd885e85904e52cd9240a4dfa51bdba77ef741e23fd`

자료를 새로 모으거나 정답을 알려 주어 재실행한 것으로 처리하지 않았다. 수정한 것은 최종 평가 전에 정리 중인 공통 실행·제출 방식이며 버전과 기록이 남아 있다.

### 실패 뒤에 바꾼 부분의 경계

- `0.1.1`은 추출 5,000·검토 8,500·형식수정 2,500으로 배분했다. 총출력 16,000은 유지했다.
- `0.1.2`는 일반적인 주장 ID 규칙을 공통 지시문에 명시하고, 그 연결만 잘못됐을 때 허용된 evidence.claim_id 경로의 문자열만 수정하도록 했다. 숫자·본문·원문 위치·선언 ID·판단과 요청 상태를 고치는 절차가 아니다.
- `0.1.3`은 모델에 보내는 계산 기록에서 중복 source_inputs만 제거했다. 원래 정보는 추출 결과에 있고, 감사용 계산 파일에도 보존했다. 모든 원문·계산·대안은 유지했다.
- `0.1.4`는 원래 최대 5개였던 메모와 정확히 4개였던 판단을 요청의 JSON Schema에도 명시했다. 메모 개수만 잘못된 경우 메모 항목만 고치는 공통 형식 경로도 만들었다.
- 최종 성공 실행은 형식수정이 필요 없었다. 따라서 ID 패치나 메모 수정으로 최종 모델 문장을 고친 경우가 아니다.

이 기능들은 B·A0·A1이 공유할 제출 형식 처리다. A0의 실제 금융 검토 실패에 대응해 만드는 A1 전용 검사기의 효과로 세지 않는다. 최종 평가 전 공통 규칙을 고정해야 한다.

| 항목 | 최종 실행 | 공통 상한·목표 |
|---|---:|---:|

원본 요약의 비용 이름은 `estimated_cost_usd_standard_uncached`이며, 캐시 쓰기를 포함한 실제 청구서가 아니다. 최신 비용 설명은 캐시 읽기·쓰기와 실패 요청을 반영한 [사용비용](사용비용.md)과 [세부 계산](usage_costs.json)을 따른다.

## 5. 점검 결과와 남은 일

실제 Terra의 유효 제출 한 편을 확보하고, 원본·최종 JSON·Markdown·행동·사용량을 연결할 수 있음을 확인했다. 형식, 상태 처리와 자원 기록에서 추가로 막아야 할 문제는 발견하지 못했다.

이것으로 이번 요청의 **W01~W06, 첫 B 실행까지**는 결과를 확인할 수 있다. W07의 규리 채점, 파일럿 3기업 확대, 개발/평가 배정, A0/A1 개발과 최종 평가는 수행하지 않았다. 답변의 사실·방법론적 판단에 대한 최종 점수도 만들지 않았다.

실제 답변의 내용과 계산 원문 대조는 [계산·내용 점검 기록](review_actual_run_calculations.md)에 별도로 있다. 전체 작업 상태는 [작업기록](작업기록.md), 이후 순서는 [상세계획](../../whole%20plan/IPO_후속작업_상세계획.md)에서 확인한다.
